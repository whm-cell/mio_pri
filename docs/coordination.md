# 团队任务协调

用户提供目标、决定与反馈，Agent 从当前公共 PRD／规格形成执行任务，按本页判断拆解、C0/C1 和下一步，并用仓库 CLI 维护本人 `.work`。需要能读取仓库指令、编辑文件和执行命令的 Agent 及项目工具链；个人 Skills 可选，CLI 不自行理解 PRD 或后台调度。先选当前动作，再按需展开，不沿链接通读所有细则。

| 当前动作           | 仓库入口                             | 何时再展开                         |
| ------------------ | ------------------------------------ | ---------------------------------- |
| 新成员／新目标     | `pnpm work guide start`              | 拆解并核对当前任务后选择 implement |
| 恢复／核对进度     | `pnpm work context <task> resume`    | 按真实下一步选择动作               |
| 已授权实施         | `pnpm work context <task> implement` | 候选可验证时选择 verify            |
| 检查／验收         | `pnpm work context <task> verify`    | 证据齐全后选择 deliver             |
| 准备／完成交付     | `pnpm work context <task> deliver`   | 实际接受后发布报告并按需交接       |
| 跨人／跨工作区交接 | `pnpm work context <task> handoff`   | 接收后选择 resume                  |
| 完成、取消或暂缓   | `pnpm work context <task> archive`   | 显式新目标才重开                   |

表中命令由 Agent 按需调用。`guide` 导航公共规则，`status` 定位记录，`context` 核对选中任务，`read` 展开省略内容；当前核验的使用条件见[核对与同步](work-records.md#核对与同步)。列表阶段与未展开的必要授权／阻塞不能作为就绪结论。C0/C1 属于同一 `.work` 任务记录。

新 checkout 尚无 CLI 依赖时，先核对项目、锁文件、授权范围和本次缓存/临时写入位置，执行一次 `pnpm install --frozen-lockfile --ignore-scripts` 并保留结果；CLI 可用后按实际事实建档，不把初始化前的执行倒填为 C1。缺依赖的 `pnpm work` 不自动安装；初始化后的依赖增改仍经过任务 `work exec`。

## 共同规则

- 当前 Agent 在成员自己的 checkout/worktree 自动维护独立的 `.work`，保存个人过程与原件；每个执行任务一个记录，只设一个负责产物与记录的任务写入者。团队需求、PRD、专属设计与待评审提案放 `docs/tasks/` 或明确的团队来源，现行规范在 `docs/` 的其他领域页面维护，跨人交接取回公共分类资料或本人的 inbox。归属按用途与读者决定，用户指定私人用途时遵循指定；采纳状态单独标记，私人笔记不另立授权或需求。
- 先核对人类目标、范围、非目标、授权、验收和停止条件，选择最小已授权下一步。影响公共契约、权限、数据或外部副作用的未决取舍，只暂停依赖它的动作。
- 原始证据绑定实际候选，保留失败与未知。自动检查、独立审查、业务观察和人类接受分别判定；缺少能力或材料时如实记录，不能相互替代。
- 按[核对与同步](work-records.md#核对与同步)取得当前现场核验；发现变化先审阅影响，再有理由地 `work sync`。记录标签、脚本通过和聊天摘要不能代替真实差异与证据。
- 任务完成不自动授权下一功能、提交、上传、推送或部署。未知外部结果须沿原请求身份核对，不为补证重发。

### 短句意图与下一步

用户表达目标，Agent 负责定位任务、选择动作并执行；下面是语义示例，不是固定口令。先从当前对话的明确对象，结合 `status` 与任务索引找到原记录，再取对应 `context`。不能仅按最近修改时间选任务或把所有 pending 一并完成；多个对象确实无法区分时，只列简短名称请用户选择，不要求提供 ID／哈希／JSON。

| 用户意图与当前事实                                                                      | Agent 的下一步                                                                                                                                         |
| --------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------ |
| “继续”“推进当前任务”                                                                    | 复用原目标与授权，按现场进入实施、验证或交付；不重复建档，也不因一句“继续”补写接受。                                                                   |
| “先验证”“检查是否完成”                                                                  | 核对验收及有效证据，执行授权内缺少的验证，报告结果；只检查的请求不扩大为修复或接受。                                                                   |
| “让当前任务进入 complete”，结果尚未完成或证据不足                                       | 将 complete 作为推进目标，在原授权内实施／修复、补证并 prepare；不能跳过门槛。新结果交回后，若尚无针对它的接受，只需询问“这项结果是否接受并完成交付？” |
| 已交回任务、结果与限制，用户说“这项进入 complete”“可以，完成交付”，对象明确且候选仍匹配 | 该自然语言本身可表达对已交回结果的接受及执行授权；核对就绪后直接 complete，并读回该成果、附件和 PRD 索引，不再要求复述完整接受模板。                   |
| “怎么进入 complete”，或请求维护包含这句话的示例／入口                                   | 回答问题或维护指定入口；咨询、引用和举例不是实际完成指令，不能据此接受现有任务。                                                                       |
| 目标任务已经 complete，用户再次要求完成                                                 | 核对已接受候选和产物，返回现有结果；若该任务的受验内容或契约有新改动，则核对当前授权后按重开处理，不重复接受或覆盖历史。                               |

上述 complete 用于明确开发成果。当前对象是护栏维护、检查或流程任务时，说明实际验证与限制，按需 archive 收尾；不为申请公共 complete 而把它关联成 PRD 开发成果。

以上动作都先核对现场：仅提交／分支引用变化且相关内容相同，审阅后 sync 即可复用同候选证据；内容或契约变化则重验受影响项并刷新报告，不把旧接受移到新候选。关键范围／权限未知只暂停依赖它的动作，已有授权内工作继续。推进时简短说明当前任务、下一步及真正缺少的决定，交付仍披露范围、候选、报告、证据与限制；任务 ID、候选和接受来源由 Agent 从真实上下文绑定，不能靠关键词自动填造。该入口由 Agent 执行，CLI 保持既有一致性检查。

## 开始任务

先从[资料导航](index.md)定位需求与现行契约，经[成果索引](tasks/index.md)核对相关已有结果。按[创建任务](work-records.md#创建任务)明确成果归属、验收目标与方法，读回实际保存值后再实施；维护／检查无需制造业务成果。

收到目标或“继续”时，先区分只讨论、文档编制、代码实施、查看状态或交付。只讨论且未要求文件时保持只读；请求文档即按共同规则编制，候选保留待定状态，不因此启动代码实施或发布。现有明确授权继续有效，不因换阶段重复索要同一许可。

### 从需求形成执行任务

1. **定位当前目标。** 从 `status` 和公共来源核对当前 PRD、用户授权、已有结果和未完成项。每份 PRD 是独立需求，不因大小、时间或共享模块推断主从；一份需求内部可有多个执行任务。
2. **按可验证的结果拆分。** 每项写清产物、范围／非目标、前置条件和验收方法。只有结果可分别核验、依赖或写入责任不同，才拆开；小改动可直接作为一个任务，不按文件、技术层或固定数量机械拆分。必要的错误处理与回归随结果交付，不另列为可跳过的尾项。
3. **明确实际依赖与未知。** 指出所需契约、数据、权限、生命周期或外部副作用由谁提供，引用可取得的版本或公共来源。只有会改变当前任务这些边界的未知才阻塞 C0；缺少实现后的测试结果属于 C1。与当前任务无关的 OPEN 项留在公共计划或对应任务，不塞入本任务的 blockers／decisions 导致全部停工。
4. **选最小就绪任务。** 在当前授权和依赖允许的范围内选择下一项。实施任务细化到可执行、可验收即停止规划；交付物是 PRD 或开发计划时，还须满足下述规划交付要求，不能只细化编制文档这一步。若有关键未知，给出最小澄清或调查动作；可独立推进的工作继续。

### 规划交付要求

请求包含 PRD、任务拆分或开发计划时，在当前 PRD 的执行计划或已有公共计划中明确被规划的本期开发单元。每个单元说明：结果与范围／非目标；C0 就绪所需的决定、授权、依赖及当前缺口和解决动作；C1 实施要点、必要依赖顺序、对应验收和接受条件。内容须能对应具体任务，通用阶段名或流程链接不能替代；允许简洁正文或表格，不强制模板、任务编号或固定步骤数量。生命周期定义引用[当前任务的生命周期](#当前任务的生命周期)，不在每份 PRD 复制一套定义。

规划可交回、开发已就绪、实现已接受分别判断。明确标注的未决及其影响范围、解决动作可以随规划交回，不得据此宣称开发就绪；有关键依赖的单元可暂保留受其约束的实施路线，决定后再细化。没有实施后的行为证据不阻塞规划或 C0，不凭“只写文档”省略本次已要求的开发安排，也不从规划通过推导代码授权。当前指令明确要求实施时沿用该授权，不重复索要同一许可。

只细化本期拟推进单元；远期或条件性单元保留必要结果、依赖和触发条件，普通小修改不补造阶段计划。C0/C1 是同一执行任务的阶段，文档编制任务的 C1 只表示文档工作；不以此代替被规划开发单元的状态，也不按阶段预建两份任务或建满所有后续记录。公共计划保存安排和决定，实际基线、候选、动态进度和原件沿既有 `.work` 记录维护，不另建 PRD 树或重复台账；未开始的执行现场不得虚填为已核对。

### 关联并建立当前记录

先查已有记录。新执行任务用 `requirement.source`、`section` 和稳定 `key` 关联实际公共章节，再用 `ensure` 建立契约；section 取当前正文中真实且唯一的标题文字，重名时选择适当的唯一上层标题，不凭印象填写或引用示例代码中的标题。已有任务复用原 ID 和 source/key；误填或改名时，读实际正文后用带 revision 的 update 更正 section，再核对候选，不能只在原件中承认错误却保留错误定位。CLI 用 Markdown AST 核对定位和结构，需求语义及拆解仍由实际审阅判断。

已有 PRD 的轻量修复、需求调整和小功能不单建 PRD。先用 `changes <prd>` 定位已有问题并读取所选正文与相关旧成果：同一逻辑问题复用变更 ID、原任务和同一 result key，独立新问题使用新 ID；具体是否同一问题由实际审阅判断。首次建档以父 PRD 的真实章节和该 ID 为 requirement，开发成果声明 `result={prd:父 PRD,key:同 ID}`。进入 C1 后形成并登记变更正文，首次给父 PRD 加索引链接，再将正文加入 sources、审阅变化并 sync；索引生成通过 `work exec <task> -- pnpm work changes <prd> --write-index`。按[资料归属](index.md#增长与归属)保留最新方案及验收，不为每轮尝试追加成果。需求变化仍同步相关权威需求与现行规范。

补修时原地修订正文，注明本轮尚待验证；旧 v5 结果在新候选重新验证并真实接受前仍只代表上次接受，正文已更新或同 key 存在不能证明新方案已接受。换工作区缺少原 `.work` 时，公共资料仅作恢复线索，不继承授权或通过；无法比较当前候选与旧接受时保留未知。登记文件仍属于相关任务候选，兄弟变更增删或移动可能触发审阅与 sync；按 key 少读正文不构成输入隔离，也不自动把整个 changes 目录加入 sources。

编制规划时，将适用的[规划交付要求](#规划交付要求)纳入当前文档任务的 `acceptance`，核对对象是其交付的开发计划，不能仅验收文档任务自身的阶段流转。续接已有任务只补当前动作确实缺少的要求，不批量重写历史记录或改判旧接受。

需求按根入口 → 当前目标 → 相关规格／API／验收章节展开。只登记实际遵循的子文档到 `sources`；索引链接不表示全文已读。新增子文档或链接调整时复核来源列表，脚本不能自动发现遗漏的业务依赖。

涉及基础设施或外部集成时，沿实际调用关系识别直接和经适配器间接使用的依赖，从[集成契约](integrations/index.md)读取已有的适用正文，登记到 `sources` 和 `plan.norms.paths`。明确本次是沿用、扩展还是改变公共约束；纯复用不要求修改规范正文，但仍核对适用性。未采用方案保留在所属任务资料，具体业务规则仍由业务规范维护，不把整个契约目录默认加载到每项任务。

写入范围涉及护栏配置中的源码根、其父目录、其中的计划路径或 `.ts` 文件时，ensure／update 自动登记 `quality-review`（method 为 review），已有同名标准保留。仅把源码列为只读 inputs 不触发；文档任务不需另加代码审查。旧记录只读续接不会迁移，漏项时 check 报错，由 Agent 核对后 update、sync。不能缩小真实写入范围来规避审查。

### 当前任务的生命周期

| 状态                  | 进入条件与下一动作                                                                                                                          |
| --------------------- | ------------------------------------------------------------------------------------------------------------------------------------------- |
| 草稿 `stage: null`    | 当前范围、授权、关键契约或验收尚不完整；只推进已授权的澄清／文档工作，不以填齐字段冒充就绪                                                  |
| `C0_READY`            | 目标、范围、授权、相关决定、基线、依赖、验收与停止条件足够开始；当前现场核验通过后用 update 进入实施。无需冻结整个 PRD 或先取得未来行为证据 |
| `C1_IMPLEMENTATION`   | 执行当前获授权修改及必要检查；结果可验证时进入 verify，不以代码存在或编译通过认定交付                                                       |
| `C1_EVIDENCE_PENDING` | 绑定候选、环境和真实原件；缺证继续验证，有实施缺陷且修复获授权则回实施。只有改变范围或关键契约才重开相关 C0 判断                            |
| `C1_RELEASED`         | 同一候选的必需证据与真实人类接受齐备，由 deliver complete 记录；只释放本任务，不代表生产发布或其他需求完成                                  |

项目阶段和以上状态是两个维度。命令负责结构、现场和原件一致性；ready=true 不能证明拆解合理或任务完成。接下来只读取当前动作的 `context`，不循环重读所有操作。

## 实施与协作

满足[生命周期条件](#当前任务的生命周期)及当前现场核验后，经 update 进入 `C1_IMPLEMENTATION`。执行最小完整修改，保留既有保护、无关改动和错误语义；缺少未来行为证据不阻止已授权实现。记录更新随实际事实或下一步变化，跨公共契约或权限的取舍回到真实人类目标。

修改任务产物或实施输入时，先建档再进入实施，按实际副作用选写入入口：安装依赖、脚本创建／修改文档、Shell 重定向、格式化和代码生成均为命令型修改，整个写入动作通过 `work exec <task> -- <argv ...>` 启动；不能因“只是文档”或调用 Python／编辑器包装的终端命令而改走直接 Shell。仅宿主原生补丁／编辑工具由 Agent 在写入前人工核对同一任务、C1、授权、现场及无其他活动写入。命令组合与重定向也必须位于受检子进程内，例子及检查边界见[实施命令](work-records.md#实施命令)。命令退出后审阅实际变化再同步，不自动取得验证或接受。

多人任务在共享交接明确范围、写入归属和固定依赖候选。独立记录不提供代码隔离：同一文件、公共契约、状态或权限存在冲突时，由一个集成责任人收口契约，再串行修改或隔离工作区。不要给未结束的写入范围再安排执行者。

依赖记录任务、团队可访问的来源与实际就绪情况；执行者核实后才能标记 ready。脚本不查询他人的私人目录。跨工作区先选择主干、固定上游提交或明确范围的未提交快照；可移动的分支名不代替可取得的代码。

一般改动执行受影响检查，交付前须有覆盖 `pnpm check` 的当前有效结论，直接执行或沿[增量复核](work-records.md#增量验证与同输入复用)建立；公共检查与业务验收的边界见 [底座规格](foundation.md)。个人候选、环境和每轮验收结果更新同一任务；只有共享契约、最后接受的交付结论或重开状态变化时更新公共资料，读取下一动作细则即可。

## 恢复与同步

先用 `status` 定位原执行任务，再取 `context <task> resume`，核对人类意图、归属、仓库／分支、相关差异、需求来源、候选、证据与下一步。按现有 stage 选择 implement、verify 或 deliver，只有任务边界改变才重新拆解。`ensure` 不重写旧契约或同步检查点；有冲突按 context 的 revision 更新。归档或不匹配记录只作历史，不能自动恢复旧指令。

发现变化先读实际 diff 与相关章节，判断范围、授权、验收或依赖是否受影响；更新必要事实后 `work sync` 写明结论。同步保留旧证据；候选变化撤回旧释放，旧通过不自动迁移。单纯 HEAD／分支变化，经核对相同文件和契约后，可继续使用同内容候选的证据。

`WORK_CONFLICT` 后先按[核对与同步](work-records.md#核对与同步)对账原意、当前授权和现场，再提交合法 update；读取或换新哈希机械重试不能代替对账，也不能假定失败的阶段转换已生效后改用 run／exec／sync 继续。

记录缺失时从公共需求、共享交接、源码和测试恢复，不能推断成未实现或已完成。缺失或损坏证据只影响依赖它的完成判断；需要补证时再展开 verify。当前源码有明确且已授权的故障就修复再验证；只读审阅不自动授予修复权限。

外部结果未知时保留请求身份，通过支持的状态／回执查询核对；重启或新成功不能抹去原未知与失败。换设备分别核对代码、记录与必需原件，路径和哈希本身不传输文件。

## 验证与接受

编码前由人类目标确定稳定验收 ID、可观察判据和 automated／review／behavior 方法。Agent 可提出拆解与测试，不能把提案当确认或降低阈值。检查覆盖真实入口、代表性正常与失败／恢复路径；缺少环境或原件保持 pending。

有效基线继续使用，变化只重验受影响范围。Agent 核对实际调用关系、入口、消费者、配置与失败恢复路径；工具核验完整文件差异、执行原件、环境适用说明及未解决观察，不自动证明语义覆盖。多个任务在同一 checkout 的相同输入与命令可显式共用检查事实；跨候选通过覆盖复核形成新的验证回执，不能改写原件或缩小输入来制造相同候选。具体接口见[增量验证与同输入复用](work-records.md#增量验证与同输入复用)。

没有可核验基线、影响不能可靠界定、检查入口／依赖／共享机制变化使覆盖依据失效，或出现无法定位范围的集成失败时执行全量。BUG 严重程度、文件数量、任务名称和阶段变化本身不触发全量；已定位失败可由实际修复及覆盖其影响的回归解除，无关通过不能清除失败。未结束的执行先恢复；性能观察、真实业务验收和人工接受不由自动检查回执代替。质量与规范审查继续按实际影响重新核对，自动检查复用不继承人工接受。

文档交回前对照用户要求核对用途、位置、入口引用和 Git 忽略状态；文档位于本地公共目录不代表已提交或已被同事取得。

在 `C1_EVIDENCE_PENDING`，任务写入者可安排经授权的审阅者用宿主原生补丁／编辑工具准备私有观察原件，无需为纯观察退回实施。安排时明确实际候选、验收项和互不重叠的原件路径；每份原件只有一个写入者，完成后交回，由任务写入者串行登记及维护状态，审阅者不能因能调用 CLI 就接管任务。单人任务沿用当前写入者，不新增角色字段或审批。

这条例外只涵盖本任务 evidence 内尚未登记的独立普通文件，内容是观察 Markdown；写入前核对路径和文件身份，不得用符号／硬链接指向其他文件，也不得改写在途日志或已登记原件。被命令或任务读取以决定执行行为的脚本、配置、fixture、预期结果及其他受验输入属于实施，即使放在 evidence 或写在 Markdown 中也不适用。脚本生成原件仍经[实施命令](work-records.md#实施命令)进入 C1 后执行；不能借 `work run`、重定向或 `.work` 位置绕过。更改候选后保留旧稿，重新观察或说明复用依据，另存绑定新候选的原件；不只改候选标签。原件声明与登记校验统一见[记录证据](work-records.md#记录证据)。

规划交付还须对照[规划交付要求](#规划交付要求)逐项审阅本期开发单元，在文档审阅和适用的 `norms-review` 中保留具体观察：缺阶段安排、阶段对象混淆、未决冒充就绪、未来行为证据被错误前置，或维护任务被迫建立开发成果，均不能判通过。已知违反要求记 fail，信息不足记 pending；明确未决及其解决动作本身不等于规划失败。CLI 只核对声明、候选与原件一致性，不自动判断规划充分性，不以标题、关键词或检查全绿代替实际审阅。

开发成果及适用的维护在 verify 前用 `plan.norms={version:2,paths,reason}` 声明现行规范和理由，执行[交回前三方对账](#交回与下一步)。paths 只指向 `docs/` 下的现行规范或必要的 README/AGENTS，不得用任务 PRD、提案、旧跳转或接受存档替代；确无规范影响允许空 paths，reason 说明判断。必要规范正文与实现一并在 verify 前修改并进入候选，不留到 complete 后再采纳或补写。

已采用的新集成在首个实现切片中形成必要公共契约，verify 前须具备正文、资料导航和消费者规范的直接引用。仅有 PRD 中的未来落点不能替代该交付物；尚未采用的能力不为满足目录形状而创建现行规范。

`norms-review` 绑定当前候选的三方观察与剩余决定；缺项或 fail／pending 不能通过。声明、原件格式及旧版本处理统一见[记录证据](work-records.md#记录证据)，维护不为此增加 result。

有候选后用 update 明确进入 `C1_EVIDENCE_PENDING`，同时给出当前 nextAction；run／evidence 不代替这次转换，阶段更新失败不能靠取证自动推进。按[记录证据](work-records.md#记录证据)保存当前候选的自动检查与实际人工观察，证据齐备后再沿[任务交付](#任务交付与重开)处理。涉及状态、恢复、权限、跨模块生命周期或重要共享契约的实质修改，安排未实施该候选的审查者；不可用时标明独立性缺口，不伪称通过。

同任务的命令执行与记录写入串行，`work run` 从启动到原件登记均在途；其间不编辑受验输入。只读审阅、各自独立原件和无冲突的其他任务可并行，登记等当前操作结束。遇到 `WORK_BUSY` 按[命令占用与异常恢复](work-records.md#命令占用与异常恢复)核对进程与原件，不删活动标记、自动重试或重跑已成功检查来绕过。

源码任务由当前 Agent 在此执行 `quality-review`，沿真实改动及调用方、被调用方核对以下三个维度。首次建立当前源码审查范围，后续使用任务基线与实际改动；相关消费者未被候选输入覆盖时先补 inputs、sync，再取证。同一候选复用有效原件，修复后核对受影响关系，不在每次保存时全仓重审。

- algorithm：说明输入规模、调用频率和时间／空间或 I/O 成本，核对重复扫描、计算、复制与请求的实际影响。分支数、嵌套或更短写法不是缺陷证据。
- unused：跟随导出、调用、注册与对外契约，检查提取后无人使用、只剩测试消费者或原调用方仍执行旧逻辑的函数／方法。框架入口、回调、外部 API 和测试支持需核实，不能只凭仓库内没有直接调用就删除。
- reuse：查找已有同职责实现，比较输入、身份、顺序、错误和副作用语义；确认可复用却重复实现时给出影响和最小修正，不为减少重复破坏模块边界或引入不必要抽象。

原件记录实际审阅范围、依据／反证与限制。已证实问题记 fail，证据不足或未执行记 pending，无支持充分的问题记 pass；不适用须说明理由。单次 helper 或相似文本仅是线索，设计建议不自动成为阻断项。字段、允许值及整体结论推导见[记录证据](work-records.md#记录证据)。

这是现有验证流程中的审查触发点：Agent 实际执行审阅，CLI 核对必需项、原件格式、候选和结论一致性。CLI 不调用模型，不认证审查者独立性，也不证明观察诚实。能力不可用保持 pending；不得用空报告、成功的测试命令或人类接受字段冒充质量审查。

执行者确认完整命令实际覆盖验收及声明输入；[记录证据](work-records.md#记录证据)区分完整检查与补测，并保留失败、输入变化和原件绑定。哈希不证明观察真实。未受影响的旧观察可保留原件并说明适用理由，不自动转成新候选通过。

正常接续只更新变化的事实：稳定目标、授权边界、验收和停止条件不因换阶段改写，当前动作写 nextAction，接受写交付记录。计划与动态过程的归属见[规划交付要求](#规划交付要求)，证据复用与变化处理见[恢复与同步](#恢复与同步)及上述验证要求；共同依据引用原件，新审阅只补差异与适用性。

未通过时区分缺证、实现缺陷和契约变化：缺证补相应观察，已授权修复则修改并重验受影响项，改变关键边界才重新核对相关 C0。当前任务待定不自动阻塞无依赖的其他已授权任务；明确开发成果通过后准备私有交付草稿，不自行记录接受，维护结果按实际验证交回。

## 任务交付与重开

从[任务资料与成果](tasks/index.md)定位所属 PRD 和所需成果键。公共记录只保存已接受能力的完成范围、逻辑入口、验证摘要、限制和接受来源；个人尝试、原件与待接受草稿留在 `.work`。一项成果接受不表示整份 PRD 完成。

交回前按[三方对账](#交回与下一步)核对需求与方案、现行规范和已接受成果；结果与剩余缺口记录在同一 norms-review，交付动作不省略该核对。

开发成果的 result 使用注册 PRD 身份和稳定 key；维护、检查和演练声明无开发成果，不调用公共 complete。契约改变先审阅、sync，再收集当前候选证据，不运行空 prepare。

全部必需验收有匹配候选和方法的通过原件后，prepare 仅生成个人草稿供审阅；代码、原件或草稿变化撤回就绪。跨人评审沿已有共享渠道取得必要材料，不默认上传。收到针对该结果与候选的真实接受后，complete 仅更新所属 PRD 的 `complete/records.json` 与 `complete/report.md`，保留其他成果，不写静态总入口或其他 PRD；同 key 新候选重新验证与接受。公开摘要不替代代码与原件，也不发布完整开发清单或将 Git HEAD 冒充候选。

交付字段、格式版本、自身输出排除、精确成果输入及旧日志处理见[交付命令](work-records.md#交付命令)和[核对与同步](work-records.md#核对与同步)。这些格式约束不改变本节的接受条件。

complete 不修改规范或采纳提案。原目标返工用带当前授权的 update reopen，撤回个人通过；新的接受之前不改旧公共结果。公共整理可以缩减存储和重复说明，但不产生新的业务接受、不改判历史验证。

无作者记录时，receive 公共成果只创建目标、引用和入口提示，不恢复代码、不比较历史文件、不继承授权、范围、验收项或通过。精确代码 handoff 仍要求取得匹配文件。维护完成、取消或暂缓可按需 archive；归档不等于验收或清理。

新交付中断沿原请求恢复并拒绝覆盖外部修改；旧草稿/旧格式日志不能发布或重放，显式重新 prepare 后使用新流程。实现保证见[工具边界](engineering/work-tooling.md#写入恢复与保留)。公共检查不读取作者原件，只验证现行公开格式、链接和一致性。

## 交回与下一步

nextAction 表示接续者现在应做的动作。阶段转换或重开须随同一次 update 给出当前下一步；命令完成后工具写入保守后继，已符合实际与授权时直接沿用，只有不准确或不足以接续时才更新。实际事实变化、冲突对账等必要 update 可一并维护下一步，不为重复确认或只读操作另写记录。交回前核对真实章节、候选、阶段、已完成与剩余项；失败、未结束执行及缺口先处理，单条通过不推导完成，报告更正不代替记录更正。工具不判断自由文本的业务语义。

交回结果前，按当前目标在同一 `norms-review` 中对账以下三方，不另建进度台账或自动同步状态：

1. 需求与方案：对照 requirement、result 的实际需求页，以及 sources 中已声明的相关设计／提案，说明本候选完成哪些要求、方案是否已采用、未完成或未采用什么；交付规划时按[规划交付要求](#规划交付要求)核对本期开发单元。相关业务来源先登记进 sources 并纳入候选；不能在报告临时引用未登记页面代替受验依赖。没有独立设计时说明真实理由，不造空文件；普通规范与导航不机械重复成需求观察，维护规范章节本身作为需求来源时按实际关系核对。
2. 现行规范：逐页核对 norms.paths 的当前摘要、行为覆盖、必要修订和未决边界；空 paths 也核对 reason 的无影响理由。集成契约核对本次沿用、扩展或改变的关系，公共约束变化时沿调用关系检查实际消费者并安排受影响回归；只改业务策略时不复制公共规则。实现及必要正文在 verify 前进入同一候选，未采用方案继续保留候选身份，不能因实现或交付完成自动提升采用状态。
3. 已接受成果：查实际相关 PRD／key 及其受验候选，区分旧接受、本轮新能力或同 key 更新，说明与当前源码的关系和仍未接受的内容；无相关成果时写真实理由。接受只证明当时范围，不推导整份 PRD 或当前源码已完成。实际依赖其他成果时使用现有 inputs 绑定代码、契约或必要附件，不强制整个 book 进入候选。

发现需求／方案陈述与现行规范或真实接受范围存在确定矛盾时，修正对应权威页后重验；未查清保持 pending，不能在报告另写一套状态掩盖。明确标为未采用的提案与现行规范不同，本身不算漂移；代码已实现也不能把待接受标成已接受。

原件保留上述观察、缺口、剩余决定和下一步；同一页兼具需求和规范用途时按各自关系说明。CLI 核对声明、候选页摘要、结构和结论一致性，不认证需求覆盖、采用状态、接受事实语义或人工观察真实；accepted 观察不是实时成果镜像。候选或实际资料变化后审阅差异、sync 并重验受影响项，不把自己的交付输出摘要放入候选或在 complete 后回写交付前原件。complete 后独立读回所属 PRD 的实际成果与导航，确认写入仍与所接受结果一致。

交回时说明当前候选实际完成的内容、证据、三方关系和剩余决定。维护照此交回适用观察，不强迫公共 complete；取消、暂缓或未完成交接保留缺口，不要求补造通过。草稿待接受不等于停掉所有独立工作：若已有整体实施授权，仍可选择授权内、依赖已核实且无写入冲突的下一项；需要前项接受才满足的依赖继续等待。任务完成不自动扩大授权。

需求的所有必需结果已有匹配证据和接受结论后结束该需求，不再补造阶段。后续独立需求使用自己的 PRD，引用实际受影响的现行契约；不默认维护 PRD 主从树。工作取消、暂缓或需要交接时转相应动作，保留原件与真实状态。

## 跨人交接

共享范围、契约与交付结论沿既有计划、Issue／PR 或明确的共享文档维护；没有渠道时先在仓库公共文档保存必要脱敏事实。`sharedRef` 指向同一权威来源，“本机已交接”不证明同事已取得材料。

发送方核对候选和[三方关系](#交回与下一步)后准备本地 handoff，审阅脱敏再沿授权共享。交接说明目标／非目标、范围、来源、固定代码、依赖、阻塞、实际结果与限制、下一步、停止条件，以及必要原件的取得方式；未完成观察保持缺口，草稿不上传，也不复制代码和原件。

接收方实际取得代码、文档和必要原件，再 receive。文件不匹配就拒绝创建；匹配时也只建立接收者草稿：授权清空，依赖重新核对，通过不自动继承。原报告只是转述，须取得原件后登记或按授权重跑。各成员可沿用同一任务 ID，本地执行事实独立，共同契约仍只有一个权威来源。

公共报告优先放在已有 Issue／PR。不要把包含自身候选标识的报告纳入同一候选输入造成自引用，也不把别人的 `.work` 当作共享入口。宿主能力缺失时按公共契约继续可独立工作，缺少的业务或审查能力不伪称通过。

## 归档与保留

完成、取消或暂缓时由 Agent 按需原地 archive，按[交回与下一步](#交回与下一步)保留三方核对结论、未完成项和理由。取消／暂缓不以通过全部审查为前提，archive 不表示接受或验证通过。历史不自动成为下一任务；重开前核对新目标和授权，通过带当前授权的 `update` 显式 reopen，再核对候选与下一步。没有自动归档、删除、备份或定时清理。

保存必要的原始日志、截图、trace 与不可重建失败输入；可重建 fixture 放系统临时目录，不复制整仓库作续接资料。没有备份即仅本机可用，传输、保留期和清理沿真实项目选择，不根据日期或容量直接删除。

## 实现依据

文档规定判断，命令核对可确定事实；每位成员的本地 check 与公共 CI 分开。CI 验证工具、公开契约和测试，不能证明未提交的私人记录或人工观察。Skill 是可选辅助，根入口和这些命令构成项目自身的执行路径。

记录身份、渐进读取、成果存储与恢复的实现保证集中在[工具边界](engineering/work-tooling.md)，不在本页重复实现历史。CLI 保留单写入者与 revision 冲突保护，不认证人工观察或宿主是否遵循读取路线；仅在实际目标、事实或下一步变化时更新记录。

当前验收入口见 [验收说明](acceptance.md)，任务交付按 [索引](tasks/index.md) 查找，完整字段见 [记录结构](work-records.md#记录结构)。只有需要更新格式或排查未知字段时才展开字段表；普通任务不加载历史验收。新增边界或动作时验证真实合法／违规导入和独立入口行为，目录名与关键词不作为证据。
