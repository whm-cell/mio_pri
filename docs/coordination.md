# 团队任务协调

用户提供目标、决定与反馈，Agent 从当前公共 PRD／规格形成执行任务，按本页判断拆解、C0/C1 和下一步，并用仓库 CLI 维护本人 `.work`。需要能读取仓库指令、编辑文件和执行命令的 Agent 及项目工具链；个人 Skills 可选，CLI 不自行理解 PRD 或后台调度。先选当前动作，再按需展开，不沿链接通读所有细则。

| 当前动作           | 仓库入口                             | 何时再展开                         |
| ------------------ | ------------------------------------ | ---------------------------------- |
| 新成员／新目标     | `pnpm work guide start`              | 拆解并核对当前任务后选择 implement |
| 恢复／核对进度     | `pnpm work context <task> resume`    | 按真实下一步选择动作               |
| 已授权实施         | `pnpm work context <task> implement` | 候选可验证时选择 verify            |
| 检查／验收         | `pnpm work context <task> verify`    | 证据齐全后选择 deliver             |
| 准备／完成交付     | `pnpm work context <task> deliver`   | 实际接受后发布报告并按需交接       |
| 跨人／跨工作区交接 | `pnpm work context <task> handoff`   | 接收后选择 resume                  |
| 完成、取消或暂缓   | `pnpm work context <task> archive`   | 显式新目标才重开                   |

表中命令由 Agent 按需调用。`guide` 不要求本地记录，`context` 返回当前任务摘要、revision、核对结果和该动作正文。`status` 可在首次运行时查看空列表，已有任务按需求关联查找，并只读核对当前候选、原件与待接受条件；历史证据与完整结构只在确有问题时定位读取。C0/C1 是 `.work/tasks/<task-id>/state.json` 的阶段字段，不是同名目录；公共交付从任务索引查找。索引、完整文件摘要校验和向模型输出正文是不同职责。

## 共同规则

- 当前 Agent 在成员自己的 checkout/worktree 自动维护独立的 `.work`，保存个人过程与原件；一个执行任务一个记录和写入者。团队需求、PRD、设计及跨人交接（含待评审稿）放公共文档区或明确的团队来源。归属按用途与读者决定，用户指定私人用途时遵循指定；采纳状态单独标记，私人笔记不另立授权或需求。
- 先核对人类目标、范围、非目标、授权、验收和停止条件，选择最小已授权下一步。影响公共契约、权限、数据或外部副作用的未决取舍，只暂停依赖它的动作。
- 原始证据绑定实际候选，保留失败与未知。自动检查、独立审查、业务观察和人类接受分别判定；缺少能力或材料时如实记录，不能相互替代。
- 先 `work check` 核对现场；发现变化后审阅影响，再有理由地 `work sync`。记录标签、脚本通过和聊天摘要不能代替真实差异与证据。
- 任务完成不自动授权下一功能、提交、上传、推送或部署。未知外部结果须沿原请求身份核对，不为补证重发。

### 短句意图与下一步

用户表达目标，Agent 负责定位任务、选择动作并执行；下面是语义示例，不是固定口令。先从当前对话的明确对象，结合 `status` 与任务索引找到原记录，再取对应 `context`。不能仅按最近修改时间选任务或把所有 pending 一并完成；多个对象确实无法区分时，只列简短名称请用户选择，不要求提供 ID／哈希／JSON。

| 用户意图与当前事实                                                                      | Agent 的下一步                                                                                                                                         |
| --------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------ |
| “继续”“推进当前任务”                                                                    | 复用原目标与授权，按现场进入实施、验证或交付；不重复建档，也不因一句“继续”补写接受。                                                                   |
| “先验证”“检查是否完成”                                                                  | 核对验收及有效证据，执行授权内缺少的验证，报告结果；只检查的请求不扩大为修复或接受。                                                                   |
| “让当前任务进入 complete”，结果尚未完成或证据不足                                       | 将 complete 作为推进目标，在原授权内实施／修复、补证并 prepare；不能跳过门槛。新结果交回后，若尚无针对它的接受，只需询问“这项结果是否接受并完成交付？” |
| 已交回任务、结果与限制，用户说“这项进入 complete”“可以，完成交付”，对象明确且候选仍匹配 | 该自然语言本身可表达对已交回结果的接受及执行授权；核对就绪后直接 complete，并读回报告、附件、索引和 pending 清理结果，不再要求复述完整接受模板。       |
| “怎么进入 complete”，或请求维护包含这句话的示例／入口                                   | 回答问题或维护指定入口；咨询、引用和举例不是实际完成指令，不能据此接受现有任务。                                                                       |
| 目标任务已经 complete，用户再次要求完成                                                 | 核对已接受候选和产物，返回现有结果；若该任务的受验内容或契约有新改动，则核对当前授权后按重开处理，不重复接受或覆盖历史。                               |

以上动作都先核对现场：仅提交／分支引用变化且相关内容相同，审阅后 sync 即可复用同候选证据；内容或契约变化则重验受影响项并刷新报告，不把旧接受移到新候选。关键范围／权限未知只暂停依赖它的动作，已有授权内工作继续。推进时简短说明当前任务、下一步及真正缺少的决定，交付仍披露范围、候选、报告、证据与限制；任务 ID、候选和接受来源由 Agent 从真实上下文绑定，不能靠关键词自动填造。该入口由 Agent 执行，CLI 保持既有一致性检查。

## 开始任务

收到目标或“继续”时，先区分只讨论、文档编制、代码实施、查看状态或交付。只讨论且未要求文件时保持只读；请求文档即按共同规则编制，候选保留待定状态，不因此启动代码实施或发布。现有明确授权继续有效，不因换阶段重复索要同一许可。

### 从需求形成执行任务

1. **定位当前目标。** 从 `status` 和公共来源核对当前 PRD、用户授权、已有结果和未完成项。每份 PRD 是独立需求，不因大小、时间或共享模块推断主从；一份需求内部可有多个执行任务。
2. **按可验证的结果拆分。** 每项写清产物、范围／非目标、前置条件和验收方法。只有结果可分别核验、依赖或写入责任不同，才拆开；小改动可直接作为一个任务，不按文件、技术层或固定数量机械拆分。必要的错误处理与回归随结果交付，不另列为可跳过的尾项。
3. **明确实际依赖与未知。** 指出所需契约、数据、权限、生命周期或外部副作用由谁提供，引用可取得的版本或公共来源。只有会改变当前任务这些边界的未知才阻塞 C0；缺少实现后的测试结果属于 C1。与当前任务无关的 OPEN 项留在公共计划或对应任务，不塞入本任务的 blockers／decisions 导致全部停工。
4. **选最小就绪任务。** 在当前授权和依赖允许的范围内选择下一项。把当前任务细化到可执行、可验收即停止规划，后续保留必要结果和依赖，不提前建满所有记录。若有关键未知，给出最小澄清或调查动作；可独立推进的工作继续。

需要分阶段或协作的安排写在当前 PRD 的执行计划或已有公共计划中：任务／结果、范围、依赖、验收、未决即可，不另建 PRD 树或重复进度台账。个人进度和原件只记在 `.work`；不要求用户写 JSON 或背命令。

### 关联并建立当前记录

先查已有记录。新执行任务用 `requirement.source`、`section` 和稳定 `key` 关联实际公共章节，再用 `ensure` 建立契约；已有任务复用原 ID 和 requirement，通过 `context`、带 revision 的 `update` 维护，不因新会话或失败重试重新建档。CLI 校验结构，需求语义与拆解合理性由 Agent 负责。

需求按根入口 → 当前目标 → 相关规格／API／验收章节展开。只登记实际遵循的子文档到 `sources`；索引链接不表示全文已读。新增子文档或链接调整时复核来源列表，脚本不能自动发现遗漏的业务依赖。

写入范围涉及护栏配置中的源码根、其父目录、其中的计划路径或 `.ts` 文件时，ensure／update 自动登记 `quality-review`（method 为 review），已有同名标准保留。仅把源码列为只读 inputs 不触发；文档任务不需另加代码审查。旧记录只读续接不会迁移，漏项时 check 报错，由 Agent 核对后 update、sync。不能缩小真实写入范围来规避审查。

### 当前任务的生命周期

| 状态                  | 进入条件与下一动作                                                                                                                           |
| --------------------- | -------------------------------------------------------------------------------------------------------------------------------------------- |
| 草稿 `stage: null`    | 当前范围、授权、关键契约或验收尚不完整；只推进已授权的澄清／文档工作，不以填齐字段冒充就绪                                                   |
| `C0_READY`            | 目标、范围、授权、相关决定、基线、依赖、验收与停止条件足够开始；`work check` 核对后用 update 进入实施。无需冻结整个 PRD 或先取得未来行为证据 |
| `C1_IMPLEMENTATION`   | 执行当前获授权修改及必要检查；结果可验证时进入 verify，不以代码存在或编译通过认定交付                                                        |
| `C1_EVIDENCE_PENDING` | 绑定候选、环境和真实原件；缺证继续验证，有实施缺陷且修复获授权则回实施。只有改变范围或关键契约才重开相关 C0 判断                             |
| `C1_RELEASED`         | 同一候选的必需证据与真实人类接受齐备，由 deliver complete 记录；只释放本任务，不代表生产发布或其他需求完成                                   |

项目阶段和以上状态是两个维度。命令负责结构、现场和原件一致性；ready=true 不能证明拆解合理或任务完成。接下来只读取当前动作的 `context`，不循环重读所有操作。

## 实施与协作

确认当前任务满足 [生命周期条件](#当前任务的生命周期)，用 `work check` 核对现场后经 update 进入 `C1_IMPLEMENTATION`。执行最小完整修改并保留既有保护、无关改动和错误语义；不因缺少未来行为证据阻止已授权实现。只在范围、决定、阻塞、候选、证据或下一步变化时更新同一记录；跨公共契约或权限的取舍回到真实人类目标。

先建档再实施，安装依赖也属于实施。命令型修改通过 `work exec <task> -- <argv ...>` 启动，工具在子进程启动前核对归属、当前契约、候选、C1 实施阶段与未结束的交付操作。命令退出后不自动 sync、不算验证证据；Agent 审阅实际变化后再同步。编辑器／宿主直接写入仍由 Agent 在写入前履行相同义务，此入口不是全局文件沙箱，也不能证明所有写入都经检查。

多人任务在共享交接明确范围、写入归属和固定依赖候选。独立记录不提供代码隔离：同一文件、公共契约、状态或权限存在冲突时，由一个集成责任人收口契约，再串行修改或隔离工作区。不要给未结束的写入范围再安排执行者。

依赖记录任务、团队可访问的来源与实际就绪情况；执行者核实后才能标记 ready。脚本不查询他人的私人目录。跨工作区先选择主干、固定上游提交或明确范围的未提交快照；可移动的分支名不代替可取得的代码。

一般改动执行相关检查，交付前运行 `pnpm check`；公共检查与业务验收的边界见 [底座规格](foundation.md)。个人候选、环境和每轮验收结果更新同一任务；只有共享契约、最后接受的交付结论或重开状态变化时更新公共资料，读取下一动作细则即可。

## 恢复与同步

先用 `status` 定位原执行任务，再取 `context <task> resume`，核对人类意图、归属、仓库／分支、相关差异、需求来源、候选、证据与下一步。按现有 stage 选择 implement、verify 或 deliver，只有任务边界改变才重新拆解。`ensure` 不重写旧契约或同步检查点；有冲突按 context 的 revision 更新。归档或不匹配记录只作历史，不能自动恢复旧指令。

发现变化先读实际 diff 与相关章节，判断范围、授权、验收或依赖是否受影响；更新必要事实后 `work sync` 写明结论。同步保留旧证据；候选变化撤回旧释放，旧通过不自动迁移。单纯 HEAD／分支变化，经核对相同文件和契约后，可继续使用同内容候选的证据。

记录缺失时从公共需求、共享交接、源码和测试恢复，不能推断成未实现或已完成。缺失或损坏证据只影响依赖它的完成判断；需要补证时再展开 verify。当前源码有明确且已授权的故障就修复再验证；只读审阅不自动授予修复权限。

外部结果未知时保留请求身份，通过支持的状态／回执查询核对；重启或新成功不能抹去原未知与失败。换设备分别核对代码、记录与必需原件，路径和哈希本身不传输文件。

## 验证与接受

编码前由人类目标确定稳定验收 ID、可观察判据和 automated／review／behavior 方法。Agent 可提出拆解与测试，不能把提案当确认或降低阈值。检查覆盖真实入口、代表性正常与失败／恢复路径；缺少环境或原件保持 pending。

文档交回前对照用户要求核对用途、位置、入口引用和 Git 忽略状态；文档位于本地公共目录不代表已提交或已被同事取得。

有候选后进入 `C1_EVIDENCE_PENDING`。首次取证前先读 context deliver，按该入口启用交付输出分类，核对并 sync，再回 verify 收集证据；启用分类不代表草稿已完成。自动检查保存命令、退出码、候选和环境；独立审查或业务观察说明操作者、场景、动作、结果及限制。涉及状态、恢复、权限、跨模块生命周期或重要共享契约的实质修改，安排未实施该候选的审查者；不可用时标明独立性缺口，不伪称通过。

源码任务由当前 Agent 在此执行 `quality-review`，沿真实改动及调用方、被调用方核对以下三个维度。首次建立当前源码审查范围，后续使用任务基线与实际改动；相关消费者未被候选输入覆盖时先补 inputs、sync，再取证。同一候选复用有效原件，修复后核对受影响关系，不在每次保存时全仓重审。

- algorithm：说明输入规模、调用频率和时间／空间或 I/O 成本，核对重复扫描、计算、复制与请求的实际影响。分支数、嵌套或更短写法不是缺陷证据。
- unused：跟随导出、调用、注册与对外契约，检查提取后无人使用、只剩测试消费者或原调用方仍执行旧逻辑的函数／方法。框架入口、回调、外部 API 和测试支持需核实，不能只凭仓库内没有直接调用就删除。
- reuse：查找已有同职责实现，比较输入、身份、顺序、错误和副作用语义；确认可复用却重复实现时给出影响和最小修正，不为减少重复破坏模块边界或引入不必要抽象。

原件记录审查者、实际范围、候选、各维度的依据／反证、结论和限制。已证实问题记 fail；证据不足或未执行记 pending；无支持充分的问题记 pass。不适用记 not_applicable 并说明理由，例如核对 diff 后只有格式变化。单次 helper 或相似文本仅是线索，设计建议不自动变成阻断项。三个维度全部 pass／not_applicable 才能登记整体 pass；有 fail 为 fail，否则有 pending 为 pending。格式见本动作返回的记录证据说明。

这是现有验证流程中的审查触发点：Agent 实际执行审阅，CLI 核对必需项、原件格式、候选和结论一致性。CLI 不调用模型，不认证审查者独立性，也不证明观察诚实。能力不可用保持 pending；不得用空报告、成功的测试命令或人类接受字段冒充质量审查。

`work run` 比较前后内容以及已有输入文件／源目录的身份、修改与变更时间，发现临时改写后恢复也不算通过。该核对依赖文件系统元数据，不是沙箱或任意中间行为追踪；执行者仍须确认命令检验了声明的输入。`work evidence` 绑定已取回的人工原件，哈希不证明观察诚实。

每项必需验收有匹配候选和方法的通过原件，并已获得针对该候选的真实人类接受后，由 `deliver complete` 记录 `reviewDecision: ACCEPT`、`stage: C1_RELEASED`、`releaseDisposition: RELEASED`。这只释放当前切片，不是生产就绪或外部操作授权。脚本检查结构和原件一致性，不认证人工标签的来源。

旧释放原件缺失或损坏时，显式 run／evidence 允许补证并重置接受结论；当前授权、依赖和上下文门槛仍有效。旧失败保留；未受影响证据可人工论证复用，但命令不会自动重新绑定旧证据，原件与理由必须可审阅。

未通过时区分缺证、实现缺陷和契约变化：缺证补相应观察，已授权修复则修改并重验受影响项，改变关键边界才重新核对相关 C0。当前任务待定不自动阻塞无依赖的其他已授权任务；通过后准备交付草稿，不自行记录接受。

## 任务交付与重开

交付报告归属于稳定任务 ID，记录最后一次已接受的交付快照。实施者是元数据，不按人名或日期拆目录。资料归属沿共同规则；历史报告不能覆盖当前契约。

从 [任务索引](tasks/index.md) 按需求或模块定位，再读相关报告和必要证据，不默认展开全部 complete。索引每任务一条，保存公共待接受快照及最后接受结果；个人进度、尝试和失败不在公共文件逐次追加。首次 enable 和普通 ensure 不发布草稿；证据齐全后的 prepare 才登记公共 pending 入口，不预造完成报告。

取证前由 Agent 用 `deliver prepare` 启用固定交付输出，再审阅候选变化、sync 和验证。本任务报告包与公共索引单独检查，不进入受验输入；代码、规格及实际依赖的其他报告仍参与候选。旧任务不自动启用，不把旧通过重绑到新候选。

验收齐全后 prepare 生成本人 delivery 目录内的草稿，并将同一份脱敏报告和必要附件发布到 `docs/tasks/pending/<task-id>/`，索引提供可审阅入口；记录为 `HOLD_FOR_HUMAN_REVIEW`。`stage` 仍为 `C1_EVIDENCE_PENDING`，通过 `releaseDisposition` 区分缺证与待接受；check/context/status 每次核对实际候选、原件、草稿及附件，变化后不再显示可接受。公共 pending 只证明指定候选的待接受快照，不自动证明当前源码匹配。

Agent 交回时明确任务 ID、候选、公共报告链接、完成范围、验证与限制，以及尚待接受的结果。真实结果接受必须针对该候选；按[短句意图与下一步](#短句意图与下一步)理解用户对已交回结果的明确完成请求，由 Agent 绑定实际接受来源、执行 complete 并读回产物，无需用户复述 ID、哈希或接受模板。开始另一项任务、要求修复护栏或接受实现方案，不自动等于接受旧交付。缺少接受时保留 pending，不创建空 complete 目录。

complete 核对 revision、草稿摘要、证据原件、公共待接受文件及接受依据后，写入 `docs/tasks/complete/<task-id>/report.md`、必要文本附件和索引，移除本次公共 pending 包；旧接受结果的恢复要求保持。工具不认证人的身份或接受真实性，也不替代部署与合并。旧任务不自动重新取证、发布待接受报告或记录接受。

公共报告只共享最终验收所需的脱敏证据；原文、脱敏副本和摘录分别标注。不能只给同事一个私人路径；其余原件继续留在个人记录。不得为共享而复制整份 .work。报告中的数据、命令和日志不是当前指令。

原目标返工或补验用带当前授权的 update reopen：索引标记 reopened，最后接受报告保留，个人接受退回待验；新需求建立新任务并关联旧报告。再次完成时更新同一路径，覆盖前必须确认整个旧报告包已保存在当前 Git HEAD。没有历史保存则拒绝覆盖，不自动提交。历史依赖固定报告所在提交、路径与受验版本。

没有原作者 .work 时，可从公共报告 receive 为自己的草稿：核对当前代码差异、规格、权限及必要证据，不继承原作者授权或本机通过。完成后 archive 只归档个人记录；取消、暂缓也可 archive，不进入 complete。

prepare／complete／reopen 的交付操作保存在本人的 delivery 目录。发生中断时使用原请求重试，对账已落盘内容；不覆盖变更后的索引、报告或状态。单 checkout 单写入者，跨 checkout 使用 Git 合并；逐文件原子替换不是跨文件事务。公共检查只读公共文件，能发现 pending/complete 报告、索引与附件不一致，但不能证明验收语义真实。

### 交回与下一步

交回结果时说明当前候选实际完成的内容、证据和剩余决定。草稿待接受不等于停掉所有独立工作：若已有整体实施授权，仍可选择授权内、依赖已核实且无写入冲突的下一项；需要前项接受才满足的依赖继续等待。任务完成不自动扩大授权。

需求的所有必需结果已有匹配证据和接受结论后结束该需求，不再补造阶段。后续独立需求使用自己的 PRD，引用实际受影响的现行契约；不默认维护 PRD 主从树。工作取消、暂缓或需要交接时转相应动作，保留原件与真实状态。

## 跨人交接

共享范围、契约与交付结论沿既有计划、Issue／PR 或明确的共享文档维护；没有渠道时先在仓库公共文档保存必要脱敏事实。`sharedRef` 指向同一权威来源，“本机已交接”不证明同事已取得材料。

发送方核对候选后准备本地 handoff，审阅脱敏再沿授权共享。交接说明目标／非目标、范围、来源、固定代码、依赖、阻塞、实际结果与限制、下一步、停止条件，以及必要原件的取得方式；草稿不上传，也不复制代码和原件。

接收方实际取得代码、文档和必要原件，再 receive。文件不匹配就拒绝创建；匹配时也只建立接收者草稿：授权清空，依赖重新核对，通过不自动继承。原报告只是转述，须取得原件后登记或按授权重跑。各成员可沿用同一任务 ID，本地执行事实独立，共同契约仍只有一个权威来源。

公共报告优先放在已有 Issue／PR。不要把包含自身候选标识的报告纳入同一候选输入造成自引用，也不把别人的 `.work` 当作共享入口。宿主能力缺失时按公共契约继续可独立工作，缺少的业务或审查能力不伪称通过。

## 归档与保留

完成、取消或暂缓时由 Agent 按需原地 archive，保留未完成项和理由。历史不自动成为下一任务；重开前核对新目标和授权，通过带当前授权的 `update` 显式 reopen，再核对候选与下一步。没有自动归档、删除、备份或定时清理。

保存必要的原始日志、截图、trace 与不可重建失败输入；可重建 fixture 放系统临时目录，不复制整仓库作续接资料。没有备份即仅本机可用，传输、保留期和清理沿真实项目选择，不根据日期或容量直接删除。

## 实现依据

文档规定判断，命令核对可确定事实；每位成员的本地 check 与公共 CI 分开。CI 验证工具、公开契约和测试，不能证明未提交的私人记录或人工观察。Skill 是可选辅助，根入口和这些命令构成项目自身的执行路径。

职责分为记录持久化、结构化建档／更新、候选／原件核对、交接与动作阅读。此前手工命名和直接改 JSON 容易让同一子任务重复建档、续接丢进度或误改证据；在现有 CLI 加入需求关联、稳定 ID 和受限 update，复用原保存／哈希能力，比另建任务平台成本低。新增维护成本是请求字段白名单、身份规则和恢复测试；已有 v1 记录不迁移。仅在实际任务或下一步变化时调用，避免把记账变成额外流程。

单任务单写入者，revision 检查拒绝过期请求，保存前检测命令期间改动；这些保护不能宣称跨进程事务或分布式锁。无新依赖、常驻调度或默认全量正文加载。完整文件摘要用于完整性，模型正文按动作取用；文档存在和命令通过不能证明 Agent 遵循了读取路径，也不能保证任意宿主自动调用工具。

当前验收入口见 [验收说明](acceptance.md)，任务交付按 [索引](tasks/index.md) 查找，完整字段见 [记录结构](work-records.md#记录结构)。只有需要更新格式或排查未知字段时才展开字段表；普通任务不加载历史验收。新增边界或动作时验证真实合法／违规导入和独立入口行为，目录名与关键词不作为证据。
