# auth 与基础 HTTP 的复用及护栏改进方案（有限实施，待接受）

<a id="auth-与基础-http-的复用及护栏改进方案待评审"></a>

从 [S0 设计](design.md)拆出的复用方案。当前已获授权并实施下述路径常量、共同响应原语、正文局部常量和 helper 依赖边界；开发候选的验证按同候选证据判定，实际接受沿现有流程，尚未成为人类已接受成果。本文保留设计取舍与有界试点方法，实际能力由现行规范维护，不追加执行流水。

现行协议仍以[认证域](../../apis/auth.md)和[Foundation 域](../../apis/foundation.md)为准，共同能力由[运行时公共能力](../../apis/index.md#运行时公共能力)发现；原认证成果的接受范围保持独立。只采用本次有限抽取和必要依赖检查，身份新接口、共享正文读取器、相似发现工具及自动抽取平台均未采用。

#### 当前事实与改进目标

`authOptions` 和 `readAuthConfig` 已由 [运行时](../../../src/auth/service.ts)、[插件装配](../../../src/plugin.ts)及[显式迁移](../../../scripts/service/migrate-auth.ts)按各自职责复用；密码、Cookie 签名和会话管理已经委托固定版本的认证库。问题不是没有公共能力，而是后续开发需要更准确地识别共同知识与协议差异。

[原认证审查](../history/complete/auth-registration-foundation-ac88ccd0f34f1c0c/evidence/quality-review.md)已看到两个 HTTP 处理器的相似实现，基于身份、Cookie、方法和库错误响应差异保留独立处理器。这一判断不排斥更小的响应原语抽取。当前 [AST 检查](../../../scripts/harness/check-source.ts)检查依赖和代码形态，[quality-review 工具](../../../scripts/harness/work/quality-review.ts)校验人工审查原件；两者都不自动判断语义复用。缺少相似代码检测器不能作为本例保留独立处理器的直接原因。

具体改进目标是：共同响应头和包装层错误只维护一份；认证前缀只有一个权威值；后续业务知道从哪里取得响应能力和可信身份。不得借此合并本来不同的认证、来源策略或库响应。

| 认证配置与库选项     | 保持 `readAuthConfig`、`authOptions` 的现有归属和调用链                                                                                                      | 运行时与迁移继续共用，不复制第三份配置或表模型                            | 配置/迁移不一致是现有共享已防范的问题；无需再包一层配置服务、迁移框架或 DB 池工厂                                                                                                  |
| 可信身份             | 保留 `Authentication.identity(headers)`；首个项目 HTTP 适配器需要时注入身份解析能力，应用服务只接收已验证的主体值                                            | `/api/v1/me` 已实际使用；未来项目服务接收可信 `userId` 后另行判断归属     | 不能让请求体、服务 Bearer 或 HTTP/认证驱动类型进入应用层代替授权。当前不额外导出无人消费的 IdentityService；项目任务再确定需要 `userId` 还是含 `sessionId` 的窄契约                |
| 完整处理器和来源校验 | 保留两个处理器、认证路由白名单、库转发与各自配置校验                                                                                                         | Foundation 与认证入口各自消费                                             | 通用 router、统一 CORS/认证策略、通用成功响应器会引入分支和误用面；精确 Origin 校验的局部相似也不足以合并认证 BASE_URL 的额外约束。当前收益不足，后置                              |

响应原语的签名示意如下；`JsonContentType` 是该模块内的窄类型，不引入可扩展策略对象。

```ts
type JsonContentType = 'application/json' | 'application/json; charset=utf-8';

// 每请求调用一次：生成服务端 requestId，设置 no-store、nosniff 和 X-Request-Id。
declare function startHttpResponse(response: ServerResponse): string;

// 仅包装层错误：写入 { error: detail }，保留调用方的状态、消息和 Content-Type。
declare function writeApiError(
  response: ServerResponse,
  status: number,
  detail: ApiError['error'],
  contentType: JsonContentType,
): void;
```

`writeApiError` 只序列化一次错误体，不解析 Cookie、不生成业务错误码、不添加重试或重复边界校验。Foundation 仍传现有可读消息和带 charset 的 JSON 类型；认证包装错误仍传现有 code/message 和不带 charset 的 JSON 类型。成功 JSON 和无正文响应继续留在各处理器，不为了复用再导出一套成功响应 API。实施时删除两个调用方中被替代的共同头和错误序列化逻辑，不能只新增 helper 而保留旧路径。

#### 必须保留的差异

| 边界           | 抽取时保持的行为                                                                                                                                                                                             |
| -------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| 来源检查及顺序 | 无效 Origin 的拒绝先于路由、方法和凭据处理；认证已知路由的 POST 与预检要求 Origin，未知路由仍先返回 404。Foundation 的无 Origin 调用和预检规则保持不变；不得把允许 Origin 当作身份验证                       |
| CORS 与身份    | 认证允许 Cookie 凭据，预检为目标方法与 Content-Type；Foundation 为 GET/Authorization 且不启用 Cookie 凭据。服务 token、会话身份和业务归属仍是三种不同判断                                                    |
| 认证库响应     | 保留库的状态、原始响应体和响应头转发；继续排除其 cache-control，并通过 `getSetCookie()` 分别转发多个 Set-Cookie。不能将库的 `{code,message}` 或限流响应重新包装为 `ApiError`，也不能将 Cookie 合成一个字符串 |
| 204 与 JSON    | 两域预检均无正文；Foundation 当前仍写入 `application/json; charset=utf-8`，认证预检不经 JSON writer。不能因共享错误写入器而给 204 添加错误体，或统一现有 Content-Type                                        |
| 身份与生命周期 | `/me` 只验证、不刷新会话；刷新仍经能传回 Cookie 的库入口。直接连接地址覆盖客户端 IP 头，正文有界读取及监听器/定时器清理、启动失败关闭池、卸载清理和工具拒绝顺序均保留                                        |

来源与方法的最小回归矩阵如下；“未知路由”均位于各自已注册的 API 前缀内，避免把 DSH 自身的未匹配响应误当处理器结果。

| 请求组合                              | Foundation                                     | 认证                                                 |
| ------------------------------------- | ---------------------------------------------- | ---------------------------------------------------- |
| 无效 Origin，同时路径未知或方法不支持 | 403                                            | 403                                                  |
| 无 Origin，已知路由 OPTIONS           | 204                                            | 403                                                  |
| 无 Origin，未知路由 OPTIONS           | 404                                            | 404                                                  |
| 允许 Origin，已知路由但方法不支持     | 405                                            | 405                                                  |
| 允许 Origin，已知路由 OPTIONS         | 204、空正文、GET/Authorization、无 Cookie 凭据 | 204、空正文、目标方法/Content-Type、允许 Cookie 凭据 |

#### 后续业务怎样发现与使用

本提案由[任务资料](../requirements.md)发现，只保留本次方案与理由。已实施能力的入口、消费者和契约在对应现行规范维护：认证配置与身份入口在[认证底座](../../auth.md)，HTTP/响应原语在[API 领域规范](../../apis/index.md)。移动或删除能力时，同一改动更新对应规范和实际调用方；后续任务从[资料导航](../../index.md)读取相关规范，再关联自己的 task。链接存在只证明可定位，不能证明消费者仍有效。

未来项目入口先读取认证规范和本域 API，按当前任务需要再读设计依据；使用响应原语处理本服务定义的错误，从装配入口取得身份解析能力，把已验证主体传给项目应用服务。应用服务不依赖 Node HTTP、DSH 或 Better Auth，也不通过响应 helper 访问数据库。新的第三方适配器遇到原始响应、流式输出或不同协议时，可以保留独立实现并说明差异，不强行复用 JSON 包装。

`src/http-response.ts` 只使用 Node HTTP 类型、UUID 能力及运行时独立的 `ApiError` 类型；不依赖 `src/auth/`、`src/plugin.ts`、驱动或开发脚本。两个 HTTP 适配器依赖该模块，装配入口仍负责创建与释放认证服务；迁移脚本继续只从已有允许的认证配置入口导入，不因抽取放宽 `scripts/service` 的依赖范围。模块方向已纳入现有 AST 检查，具体支持与限制只在[源码护栏](../../engineering/source-guardrails.md)维护。

公共能力的依据是明确职责、真实消费者或外部契约，不要求必须两个调用方。当前响应原语恰有两个消费者，身份能力仅由 `/me` 消费也可成立；反之，新增两个测试调用不能证明空组件有产品价值。只有出现共同错误字段/头变更、新业务入口、库升级或不同响应/来源协议等实际触发条件时，才重新评估独立实现或共享粒度，不在每次保存时全仓重审。

| verify：实际审阅者      | 沿 `quality-review` 的 algorithm/unused/reuse 检查：有界正文与序列化成本、导出后的真实调用、旧实现是否被替换、语义差异和未采用建议的理由。重要共享契约的实质修改由未实施者审阅             | 格式、候选与三维结论由现有工具核对；重复是否有害、公共 API 是否有价值及观察独立性仍由人/Agent 判断                                           |
| guard：护栏维护者       | 现有 AST/模块解析继续查 DSH/认证驱动边界、运行时与脚本隔离、循环、类型/构建覆盖。`check-source.ts` 对 helper 的已解析依赖增补窄允许方向，`tests/guardrails.test.ts` 维护合法和越界导入样例 | 只限制本次 helper 的模块方向，不声称已隔离全部 `src` 或形成符号级沙箱。测试含 type-only、别名/重导出等绕过路径；不以目录名或文本匹配代替 AST |

暂不修改 `quality-review` 原件格式，也不添加“相似实现即失败”的机器门槛。先让审查原件记录本次实际复用判断及反证。若后续任务反复出现搜索遗漏，才单独评估基于 AST/符号的候选发现：输出可定位的相似职责线索，由审阅者判定；先用下述正反例测量漏报、误报和维护成本，不自动抽取、不自动阻断。没有重复发生的遗漏证据时，沿调用关系搜索和对应现行规范的入口已经是更小方案。

#### 验证有效性与停止标准

当前 [Foundation 测试](../../../tests/plugin.test.ts)经真实 DSH 入口断言服务鉴权、Origin/方法、404/405、预检 204、请求标识、共同头、卸载及工具拒绝；[认证测试](../../../tests/auth.test.ts)保留真实 DB/DSH 的注册登录、会话与撤销/刷新、跨账号、持久化、Cookie 属性、来源、超大分块正文 413、限流、迁移、事务、生命周期与正式打包装载。测试内容盘点不是当前候选已通过或已接受的证据，实际原件在对应任务维护。

本次在抽取前补齐独立的响应判据，抽取后原样复用：认证包装错误头体标识与共同头、两域 Content-Type、204 空体/完整预检头、来源与路由/方法的组合顺序，以及真实库错误/限流和受控多 Set-Cookie/原始字节透传。受控上游响应只检验适配器转发，不能当作认证库已在同一场景产生多个 Cookie 的证据；不把认证业务全集重写成 helper 单元测试。正文仍缺少 16 KiB 边界与 10 秒超时的直接断言，仅将数值局部命名时保留原超限/中断回归；若后续改变读取器，再补分块字节边界、408 和监听器/定时器清理观察。

本次有限实施按以下顺序取证；设计、现行规范和指定候选的实际接受分别对账。

1. **建立行为基线。** 抽取前补充响应相关断言，经两现有实际入口和隔离数据库运行；记录状态、头、正文、Cookie 列表和可观察副作用。预期独立取自现行公开契约及抽取前观察，不导入待抽取常量或用新 helper 生成预期，避免实现改错时测试同步变绿。保留失败与未知。UUID 不比较固定值，而核对服务端生成、同响应头体一致及不同请求不沿用客户端值。
2. **同判据做前后对照。** 抽取后使用同样断言，覆盖成功、包装错误、库错误/限流、204 及来源检查优先级；证明两真实处理器都调用新原语，三处认证前缀引用同一常量，被替换旧逻辑已移除。既有正文、会话与生命周期回归保留；断流只观察可证实的清理和后续可用性，不伪称客户端已收到 400。
3. **验证职责及发现能力。** 在隔离 fixture 中执行下表对照，不为实验修改主工作区契约或公共接受记录；新 AST 规则若实施，分别运行合法/违规输入，记录实际退出和诊断。
4. **完成回归与净收益审查。** 运行相关真实 HTTP/DB 测试、打包装载和 `pnpm check`；由审阅者核对共同知识是否收敛、理解调用是否更直接、维护面是否小于新增 API/参数成本。无需凭代码行数下降或未经测量的性能收益决定采用。

步骤 3 及下表六项只用于首次采纳时的有界试点，检验护栏建议是否有效；不成为每次普通抽取或后续业务的全套新门禁。后续按受影响变化核对并复用仍适用的有效证据，只重演受影响或尚缺证的场景。

| 对照场景       | 预期观察与判定者                                                                                                                                                                              |
| -------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 可复用却重写   | 植入另一份相同包装错误/共同头实现；审阅者应找到现有 helper、指出具体维护影响并给出替换位置。仅报告“相似”不算发现完成                                                                          |
| 误合并         | 将认证库错误重新包装、合并 Set-Cookie，或套用 Foundation 的无 Cookie 预检；实际入口断言应失败，审阅者应说明为何两处理器必须保留差异                                                           |
| 提取后未使用   | 新增导出但原处理器继续旧逻辑，或仅测试调用新导出；unused/reuse 审查应判失败。类型检查通过不能作为反证                                                                                         |
| 过期入口       | fixture 移动/改名 helper 后保留旧文档链接，或保留链接但真实消费者已不用；分别由文档检查和调用链审阅发现，不把链接有效当作复用成立                                                             |
| 新业务发现演练 | 未参与实现的审阅者从现有导航定位能力，在隔离业务 HTTP fixture 中使用响应原语并说明可信身份到应用服务的传递；实际请求检验包装错误。只证明发现/复用路径，不宣称项目授权、持久化或生成业务已交付 |
| 合法独立实现   | 原始库响应、认证专用正文读取或单消费者身份边界不应仅因相似/调用少被判失败；审阅者给出输入、身份、错误或副作用差异作为保留依据                                                                 |

停止在这组最小能力的行为对照、真实消费者、必要依赖规则正反例与独立审阅齐备；未采用的内部边界不能标作机器已保护。若共同响应原语需要持续增加 Cookie/CORS/路由选项、调用方仍绕回旧实现，或共享后的维护成本没有下降，应缩减到路径常量、局部命名与审查入口，不继续建设通用平台。发现工具只有取得重复遗漏的实际证据后才进入下一项。

文档核对与静态检查只能证明相应仓库判据；代码回归证明受测行为，净收益审查判断有限抽取是否值得保留，远端 CI、真实浏览器及生产仍须各自证据。上述任一结果均不自动证明后续项目/生成能力或生产就绪，实际接受前不发布新 complete 成果。
