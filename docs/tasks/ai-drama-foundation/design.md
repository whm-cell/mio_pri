# AI 漫剧技术底座：S0 架构基线

需求来源：[技术底座 PRD](prd.md)。本文件保留 S0 设计前提、历史基线的复用理由与未来项目业务候选。认证切片已有指定候选的接受；当前运行行为以[认证底座](../../auth.md)和[API 规范](../../apis/index.md)为准，接受范围以[成果入口](complete/report.md)为准，不在本页复制运行流水。当前后端对话服务按[独立 PRD](../conversation-service/prd.md)规划，不依赖本页项目/素材/生成方案，也不能据本页认定 S1/S2 整体实现。

## 已确认前提与首期取舍

历史产品设想是单人登录后创建项目并生成，后续需要团队协作。当前已明确本仓库仅建设后端 service，先积累公共能力并接入 DSH 对话底层，不在本期实现项目或生成。单实例方向保留，多租户与前端 UI 不进入本仓库当前范围。

未来若选择项目业务，候选仍是在单插件包内按实际职责组织，项目、素材和生成记录以明确身份关联，业务授权集中在应用服务入口，团队策略届时再确定。当前不预建这些业务模块、tenant、team、角色配置、分布式调度或通用工作流框架。“单人”不表示全系统只能有一个账号；不能从请求体信任 userId，也不能因为单实例忽略实际并发。

登录方向已确认并已交付指定认证切片：由 Mio 自己提供邮箱/密码自助注册、登录和持久会话，具体行为与限制只维护在认证规范。原设计曾建议先认证、再由项目服务消费可信 userId；有限 auth/HTTP 抽取已有[独立接受成果](complete/report.md#auth-http-shared-primitives)。现有 `/me` 已消费可信身份，近期拟由对话服务消费；项目是未来条件候选，不能再排为立即下一项，也不能把“先交付认证”继续理解为未执行的首项。

## 跨层职责与依赖候选

以下保留未来项目/生成业务的单包职责候选，不是本期目录计划；名称和目录在对应业务任务获授权后按实际调用落地，不预生成空文件。近期对话的最小装配/适配边界以其独立 PRD 为准。

| 职责与候选落点                                | 对外承担什么                                                   | 允许依赖                                      | 不承担什么                                 |
| --------------------------------------------- | -------------------------------------------------------------- | --------------------------------------------- | ------------------------------------------ |
| 装配：现有 `src/plugin.ts`                    | 读取已验证配置，创建依赖，注册/撤销入口，关闭连接和执行资源    | 入口、应用服务、适配器，及公开 DSH/Cordis API | 业务规则、SQL、生成结果归属判断            |
| HTTP 适配：现有 `src/http.ts` 按需要演进      | 解析请求，取得可信身份，将命令传给应用服务，映射错误/响应      | 应用服务与公开 DTO                            | 直接执行 SQL、绕过授权访问文件或调用供应商 |
| 应用服务：按业务职责组织的 `src/projects/` 等 | 将身份、资源归属、业务规则和持久化组合成完整操作；定义事务范围 | 领域规则及本模块实际需要的存储端口            | 依赖 DSH 对象、HTTP request 或具体驱动类型 |
| 领域规则：对应业务模块内                      | 项目/资源身份、版本条件和合法变化；可独立验证                  | 业务值和纯计算                                | DB、网络、文件或开发工具 I/O               |
| 持久化适配：候选 `src/persistence/`           | 实现用例需要的查询/原子写入，维护迁移、连接和数据库错误翻译    | 所实现的业务端口、DB 驱动                     | 自行决定调用者是谁或替应用服务授予权限     |
| 媒体/供应商适配：S2 按需新增                  | 存取媒体字节，提交/查询已授权生成请求，翻译外部回执            | 实际使用的能力端口和对应客户端                | 成为业务状态和资源归属的另一套权威         |

运行时调用：入口 → 应用服务 → 持久化/供应商实现。源码依赖：应用服务依赖自己需要的端口，适配器实现端口，插件入口装配二者；接口只为真实消费者定义，不建立泛型 BaseRepository/BaseService 或额外依赖注入容器。

公开 HTTP DTO 与持久化记录分开；当前 `src/contracts.ts` 的运行时独立约束保留。后续若新增契约模块，在现有护栏中登记同样的方向和编译覆盖，不把所有类型机械塞入一个总文件。

## 身份、项目与扩展边界

本节只约束未来项目业务：被选择后可从可信用户身份、项目和项目内资源开始，不一次性设计剧本/分镜/角色/场景全量表。当前对话的最小归属是用户→对话，不引入项目，也不要求先验证项目记录。

- **可信身份**：入口经登录验证得到稳定 userId，再传入应用服务；请求中的项目 ID 只是待访问对象，不能替代授权。客户端不决定 ownerUserId。
- **项目**：具有稳定 ID、创建者/所有者身份及自身修订号。资源通过 projectId 关联项目，避免把用户名或用户目录当作资源主键。
- **首期权限候选**：应用服务对当前可信 userId 与项目所有者做一致检查，数据访问同时以归属条件限定查询/更新；模型工具、HTTP 和未来后台入口均经过该服务。
- **未来团队扩展**：新增成员关系和授权策略，在同一项目身份下解析访问权；不能简单继续把所有查询限定为所有者相等。迁移旧项目成员、权限撤销与正在执行任务的关系要由未来团队需求验收；本期不提前实现。
- **资源修订号与素材历史版本**：修订号用于防止并发覆盖，不能当作完整素材版本树。是否保留历史字节、引用固定版本还是跟随更新，在资产任务确认后再决定。

“未来可扩展”的验收范围是职责不混淆、身份和归属显式、供应商/DB实现不泄漏到业务入口；不承诺未来团队能力零迁移或零改动。

## 数据与事务路线

**当前认证切片采用 PostgreSQL。** 选型比较保留如下，SQLite是比较时的轻量备选。 当前单用户单实例本身不排斥 SQLite；偏向 PostgreSQL 的理由是服务已有独立部署定位、后续确定要团队协作，希望同一迁移与并发验证路径可继续使用。代价是增加数据库进程、备份和运维配置。本轮已为认证锁定 Better Auth 1.7.18 和 pg 8.23.1；没有为未来项目/素材预建 ORM 或通用数据层。

| 候选       | 适合当前目标的收益                                                 | 成本与采用条件                                                                               |
| ---------- | ------------------------------------------------------------------ | -------------------------------------------------------------------------------------------- |
| PostgreSQL | 明确的服务端连接、事务和数据约束；版本条件更新可经真实并发连接验证 | 需要独立数据库环境和迁移入口。首个数据任务固定版本、驱动和隔离测试方式后采用                 |
| SQLite     | 嵌入式持久化、本地设置少，适合单实例初步运行                       | 同一数据库同一时刻只有一个写入者；应测量代表性写入和排队成本，不凭“团队”二字断言它一定不适用 |

PostgreSQL 官方说明并发更新在 Read Committed 下会对更新后的行重新判断 WHERE 条件；这可以支撑 `id + expectedRevision` 的条件更新方案，但不能替代业务授权和零行结果处理。SQLite 官方给出的单写入者限制用于界定比较条件，未在本项目测得容量或延迟。[PostgreSQL 事务隔离](https://www.postgresql.org/docs/current/transaction-iso.html)、[SQLite 适用场景](https://www.sqlite.org/whentouse.html)。

首个数据任务建议直接表达少量明确的存储操作；不为尚未使用的查询引入 ORM 抽象层。当前认证使用库自带的 PostgreSQL 适配和迁移，连接释放与回滚由真实集成验证；后续业务用例的存储端口仍按消费者选择，不照搬认证表模型。

事务由应用用例定义“哪些变化要共同成立”，适配器负责 begin/commit/rollback 与连接释放。单条条件更新已足够时不增加 UnitOfWork；有多个必须一致的写入时用一个明确操作承载，不让调用方手工协调几个提交。

外部生成和文件写入不与数据库天然原子：不跨整个模型调用持有数据库事务。S2 再依据外部协议定义提交记录、结果未知、状态查询、产物写入和记录确认的顺序。没有幂等/查询依据时不自动重发，不能预先声称 exactly-once。对象存储、队列和恢复任务只在这些实际边界需要时加入。

## 组件预设到实际消费者

| 候选能力             | 消费者及最小契约                                                          | 现在做什么／暂缓什么                                                                   |
| -------------------- | ------------------------------------------------------------------------- | -------------------------------------------------------------------------------------- |
| 身份到 userId 的适配 | `/api/v1/me` 已消费；近期对话服务拟接收可信主体，未来项目服务按需消费     | 已有邮箱密码注册与会话提供，当前不为未来项目预建身份层、团队角色或付费权限             |
| 项目存储端口         | 未来项目用例的创建、按身份读取、基于 expectedRevision 更新及拒绝/冲突语义 | 项目业务被选择后才实现/测试；不是对话前置，不做全表通用 CRUD 仓库                      |
| 配置、启动与释放     | 装配入口验证必要配置，在依赖可用后注册业务入口，关闭时释放连接            | 复用当前生命周期；不把缺 DB 配置的业务入口标就绪，也不使现有纯探针无意依赖未启用数据库 |
| 业务错误映射         | 应用服务产生稳定的业务结果，HTTP 统一映射到已有错误体和 requestId         | 新用例出现时提取，不复制现有 fail/send 或提前建完整错误框架                            |
| 媒体存储             | 资产用例通过稳定引用存取字节，元数据携带项目归属                          | S2 确定媒体/保留/删除规则后实现；不在 S0 放宽运行时文件访问                            |
| 生成供应商适配       | 生成用例传已授权输入和请求身份，取得回执、查询结果和明确未知              | S2 先受控模拟器，再按已选供应商验证；保留 DSH 原循环边界                               |

每项实现必须带真实调用方、失败语义和观察点；仅列接口/文件名不算组件交付。公共函数通过已有 quality-review 核对算法成本、unused 和 reuse；没有复用关系时保留局部实现。

### auth 与基础 HTTP 的复用取舍（有限采用）

<a id="auth-http-reuse"></a>

完成范围与限制见[公共原语成果](complete/report.md#auth-http-shared-primitives)；现行符号、消费者和协议查 [API 公共能力](../../apis/index.md#运行时公共能力)、[认证职责](../../auth.md#职责与限制)及两域 HTTP 契约。本节只保留独有取舍。

| 能力             | 采用理由与边界                                        | 未采用或后置                                                            |
| ---------------- | ----------------------------------------------------- | ----------------------------------------------------------------------- |
| 认证前缀         | 一个常量供库配置、注册和匹配使用，减少同步维护        | 不建路由注册表或全局常量层                                              |
| 共同响应原语     | 共享共同头与包装错误序列化，已有两个真实处理器消费    | 完整处理器、成功响应、来源校验、Cookie/CORS 策略保持独立                |
| 正文读取         | 限制仅局部命名，当前只有认证 POST 消费                | 不共享读取器；新增同语义消费者时再评估                                  |
| 认证配置与库选项 | 运行时和迁移复用已有实现                              | 不增配置服务、迁移框架或池工厂                                          |
| 可信身份         | 已有 `/me` 消费，后续业务入口传入已验证主体并检查归属 | 现行 userId/登录 sessionId 见认证职责；不为未来项目新增无人消费的身份层 |

完整处理器的独立性来自身份、Cookie、方法和库响应协议差异；较小的响应原语共享与此相容。采用目的为减少共同知识维护点，未证明性能或生产可靠性提升。当时未观察到认证前缀故障，不以假定故障论证收益。

共享正文读取器、身份新接口、相似发现工具和自动抽取平台均未采用。只有反复出现搜索遗漏，再评估发现工具的漏报、误报与维护成本；现阶段沿调用关系搜索和现行规范入口继续。

既有 16 KiB 精确边界与 10 秒超时缺少直接断言；未来改变读取器须补分块字节边界、408 和监听器/定时器清理验证。若共享原语逐渐增加 Cookie/CORS/路由选项或维护成本上升，应重新比较局部实现。已完成试点的验证结论与未覆盖范围只在成果记录说明，不形成每次业务开发必跑的额外流程。

## 首个实现任务候选与验收

本节标题保留原设计锚点；原来的首项认证切片已经接受。**登录后的项目创建、读取和带修订号更新**仅是未来业务候选，不是当前下一项，也不构成后端对话服务的前置。认证契约见[认证底座](../../auth.md)，项目业务 API 尚未发布；下表只有在用户将项目业务选为新目标时才展开，当前本期单元和 C0/C1 安排见[对话服务 PRD](../conversation-service/prd.md#本期开发单元与-c0c1-安排)。

| 环节        | 需要明确／观察的结果                                                                                                                |
| ----------- | ----------------------------------------------------------------------------------------------------------------------------------- |
| C0 进入条件 | 登录产生可信主体；确定项目字段及初期操作；采用的 DB/驱动和迁移方式可运行；确认未授权/不存在/版本冲突的外部语义及 allowed scope      |
| 实现范围    | 消费现有可信身份、项目存储和服务、实际 HTTP 适配、必要迁移与生命周期、对应契约和测试；数据路径只使用隔离实例                        |
| 正常场景    | 登录后创建项目；通过实际入口读取同一 ID；成功更新后修订号改变；重启服务/重新连接后数据仍可读取                                      |
| 权限场景    | 未登录被拒绝；请求体伪造 owner 无效；采用的错误策略下，非所有者不能读取或更改目标。用不同测试主体验证隔离，不以首期个人使用为由省略 |
| 并发场景    | 两个请求用同一旧修订号更新，只能一个成功；另一个得到约定冲突，不能悄悄覆盖新内容                                                    |
| 故障场景    | 必须共同写入的数据在失败时不部分提交；连接、启动失败和关闭处理具有真实观察；未运行的路径保持未验证                                  |
| 护栏场景    | 合法装配/业务端口调用通过；HTTP直接导入DB、领域导入驱动、运行时导入脚本等对应违规被拦截；保持现有 DSH、动态导入和编译覆盖保护       |
| 接受条件    | 同一候选的自动检查、实际入口/DB行为、独立审查与人类接受齐备；不推导素材或生成链路已完成                                             |

未来项目名称字段范围、版本冲突码等常规细节由对应实施方案集中说明；认证载体与生命周期由认证底座契约定义，涉及资源权限的取舍届时收口。表中不含删除、转移所有权、共享成员与历史资产清理，亦未授权当前实现这些项目用例。

## 护栏增量与后续任务

认证切片的边界依据见[源码护栏](../../engineering/source-guardrails.md)，本设计不再维护另一份现行允许清单。新增项目持久化或存储适配时明确归属、允许依赖和合法/违规用例，按实际影响更新规范与 TypeScript AST 检查，不整体放开 src 的文件访问。

未来业务若新增生产目录，需要检查 sourceRoots 与模块规则的匹配顺序、类型/构建覆盖及实际打包消费者，避免仅登记目录后漏检。原有 `scripts/harness` 与 `scripts/service` 隔离保留；业务迁移是服务运维入口，不能由通用 guard 隐式执行或读取业务数据库。

后续素材与外部任务只在对应场景前提明确后展开；完整功能 PRD 到来时另行作为独立需求推进。本方案不建立新 PRD 索引或父子关系系统，实施安排统一在[当前 PRD](prd.md#81-阶段建议)。
