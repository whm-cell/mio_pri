# 项目 Redis 接入与首个认证限流切片 PRD（讨论草案）

状态：待评审。用户已授权编写本草案及任务拆分；尚未授权 Redis 业务代码实施、安装依赖、数据迁移或部署。下文“拟”“建议”及需求、验收表描述候选目标，不代表已采用规则或已实现能力。

本 PRD 覆盖项目接入 Redis，以及使用现有认证限流验证首个垂直切片。公共运行能力与认证业务规则属于同一建设目标中的不同职责，不另拆成两份重复 PRD。资料入口见[任务资料与成果](../index.md)，现行行为仍以[认证底座](../../auth.md)和[认证 HTTP 契约](../../apis/auth.md)为准。本轮只登记草案，不改写现行规范或既有接受事实。

## 1. 摘要

拟为 Mio 建立最小 Redis 运行能力，包括配置、连接生命周期和明确的消费边界；现有 Better Auth 认证限流是首个实际消费者，其计数存储拟从 PostgreSQL 切换为 Redis。项目公共接入通过这个完整业务切片验收，账号、凭据、会话和撤销继续以 PostgreSQL 为准。

首期沿用单实例服务范围。交付目标是项目 Redis 运行契约及首个限流切片的完整行为和兼容证据；性能提升、多实例容量和生产可用性需另有实际证据。优先保留现有限流语义，任何差异先明确接受范围，再实施。

## 2. 使用者与决策责任

- 开发与维护人员：需要明确的计数存储职责、真实调用入口和可复现的验证方式。
- 部署维护人员：需要明确启用条件、故障表现、切换步骤和回退边界。
- 已有账号使用者：注册、登录、续期、退出及撤销等行为应遵循已声明契约，服务中断应可识别。
- 项目负责人决定故障时的可用性取舍、允许中断、计数丢失容忍及实际部署范围；Agent 提出方案、实现已授权内容并收集证据。文档存在、检查通过或任务状态不能替代真实接受。

## 4. 目标、范围与成功标准

### 4.1 本期候选范围

- 提供项目级最小 Redis 配置与连接能力，由服务装配管理；认证限流作为首个消费者，覆盖当前库 handler 实际启用的全局、自定义及敏感操作规则。
- 提供最小服务端配置、连接建立与释放、原子计数、过期回收、明确的基础设施错误处理。
- 验证存储选择、已有账号及会话兼容、受控切换与回退，以及必要的源码边界和资料更新。
- 保留 PostgreSQL 限流路径用于既有部署兼容和受控回退；后端在启动时确定，不提供请求级混用或动态切换接口。

项目查询缓存、会话迁移、生成队列、分布式锁、通用缓存框架、多租户、多实例生产部署和模型工具授权均不在本期范围。首期不删除现有认证表，不升级认证库，不同时重写限流算法或代理信任策略。

### 4.2 可观察成功标准

1. 项目有明确的 Redis 运行入口与职责边界；在 Redis 模式下，真实认证请求的限流计数使用该能力，正常计数不再读写 PostgreSQL 限流计数；账号和会话所需数据库访问仍存在。
2. 同一请求序列在数据库基线与 Redis 候选中保持约定的放行、拒绝、窗口及响应语义，并发不会多放行。
3. 原账号、原 cookie、会话续期及撤销行为通过回归；计数故障不会被解释成身份有效或绕过认证。
4. 正常启动、失败启动、运行中断连、关闭、重新装载与受控回退均有匹配候选的证据。
5. 交付前现行规范与实现一致，适用检查及审查齐全；受控本地验证、真实部署观察和远端门禁分别报告。

性能仅记录同负载的数据库计数访问、请求延迟及资源使用。若后续把性能收益列为必需目标，先确认基线、负载及阈值；本草案不虚构提升比例或容量承诺。

### 4.3 复杂度与最小替代

依[底座规则](../../foundation.md#已采用规则与验证)的 DESIGN-OVER-001，保留以下取舍作为评审依据：

| 机制候选           | 具体问题、影响与证据边界                                                           | 最小替代、成本与本期收益                                                                               |
| ------------------ | ---------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------ |
| 引入 Redis         | 目标是验证计数存储改造；现有 DB 瓶颈及发生频率尚无证据                             | 最小替代是继续使用 PostgreSQL；新增服务、凭据、容量和故障维护成本，换取一个真实集成切片的证据          |

### 4.4 公共运行能力与消费者职责

同一个 Redis 技术不意味着所有业务使用同一套策略。首个消费者已经需要配置、连接和生命周期，因此现在划清其归属有实际依据；只实现该切片需要的能力，不预建未来缓存、队列或任意存储框架。

| 职责       | 项目 Redis 运行能力                                                  | 认证限流消费者                                                                    |
| ---------- | -------------------------------------------------------------------- | --------------------------------------------------------------------------------- |
| 配置与连接 | 客户端/服务版本、服务端秘密、连接建立/关闭、运行入口及隔离资源的事实 | 声明自己需要哪个资源及哪些操作，不持有另一套项目公共配置                          |
| 错误与重试 | 暴露可判定的连接失败、超时与结果未知；明确客户端命令重放行为         | 决定计数失败对应的 HTTP 行为、是否可恢复及限流窗口；不把 503 强加给所有未来消费者 |
| 数据与隔离 | 说明资源、命名空间和实例级策略的适用边界                             | 负责计数主体、键结构、原子消费、窗口和恢复；后续缓存的失效/回源由相应业务负责     |
| 模块与装配 | 服务装配管理生命周期；公共运行模块不反向依赖认证或其他业务           | 通过明确依赖消费公共能力，保留库的规则匹配与业务保护                              |
| 规范       | R1 在集成契约目录交付独立的 Redis 现行规范正文与导航                 | 认证规范维护自己的用法、限流语义和接口影响，并直接引用公共契约                    |

具体模块落点、公共契约与认证消费规则的边界及边界样例在 R0 确定。公共规范落点固定为 `docs/integrations/redis.md`，由 R1 在相关方案采用后随实现形成；进入 verify 前必须具备正文、[集成契约导航](../../integrations/index.md)和消费者规范的直接引用，按 AC-12 验收。当前只记录目标路径，不创建空规范或指向尚不存在页面的链接，也不把本 PRD 当作未来业务使用 Redis 的永久操作手册。

以下 RL 编号是候选需求标识，尚未生成实施任务或通过记录。

| ID                   | 候选要求                                                                                         | 兼容边界与实施前需明确的内容                                                                                                               |
| -------------------- | ------------------------------------------------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------ |
| RL-01 规则等价       | 库继续负责路径匹配、计数主体和规则选择；Redis 仅承担状态消费                                     | 按固定版本建立路径、优先级、窗口、计数更新、重试时间的对照表。错误凭据也计入进入限流器的请求；被 HTTP 适配器提前拒绝的请求不新增计数副作用 |
| RL-02 并发与窗口     | 检查额度、推进计数及设置对应过期时间是一次原子操作；使用有界键和值                               | 不直接把当前行为换成自然分钟桶、令牌桶或简单固定 TTL 计数。窗口边界、连续放行后的时间更新、拒绝是否延长窗口、临界时钟差必须有基线对照      |
| RL-03 响应与身份     | 保留现有路径、方法、Origin、CSRF、正文限制、可信 IP、cookie、安全响应头及超限响应                | 不新增客户端参数、业务身份来源或前端升级要求；已放行请求仍需正常执行凭据校验和资源归属判断                                                 |
| RL-04 会话隔离       | PostgreSQL 保持账号和会话的权威来源，`/me` 继续返回已验证身份且不刷新会话                        | 不把 Redis 当身份缓存或会话来源；原用户、原签名 secret 和原 cookie 不因计数迁移失效；保留密码更新及跨账号撤销保护                          |
| RL-05 配置与生命周期 | 未启用 Redis 时保持数据库限流；显式选 Redis 却配置不完整或启动校验失败时拒绝认证装载，不静默回退 | 配置名、客户端和服务版本、连接/命令/关闭时限在 R0 固定；连接由服务装配统一创建和释放，认证适配通过明确依赖消费，DSH 依赖仍只在插件入口     |
| RL-06 故障语义       | 建议 Redis 消费失败时拒绝受影响请求，映射为基础设施 503，而非额度超限 429                        | 候选错误体沿包装错误 `AUTH_UNAVAILABLE` 和 requestId 约定；需经真实库 handler 证明异常不会被吞掉或变为其他状态。此新增故障策略须先确认     |
| RL-07 数据与资源     | 只存限流计数及窗口所需状态，按服务、环境及模式隔离键；设置容量和回收约束                         | 不存密码、cookie、会话 token；连接秘密仅服务端注入且不入日志。测试只能清理本轮独占资源，禁止对共享实例全库清空；资源隔离方式在 R0 固定     |
| RL-08 计数保留与恢复 | 提前淘汰、重启丢失、写入失败和结果未知都有明确处理；不能把丢失状态直接认作从未请求               | 候选使用避免提前淘汰的部署策略，如 noeviction；容量耗尽拒写仍按 RL-06 处理。持久化不能替代丢失容忍与恢复承诺；见第 6 节                    |

特别需要核对 Better Auth 的接入范围：配置全局 `secondaryStorage` 默认会改变会话存储。候选方案优先评估固定版本公开的 `rateLimit.customStorage`，将改动限定于限流；不能仅为了接入计数而顺带改变会话、验证数据或数据库迁移模型。当前源码和已安装固定版本支持上述评估入口，仍需 R0 核对公开类型与真实行为。[官方会话说明](https://github.com/better-auth/better-auth/blob/main/docs/content/docs/concepts/session-management.mdx)

`RL-06` 的影响不仅是不能登录：`/api/auth/get-session`、退出、密码更新和撤销等经过库限流的入口也可能因 Redis 故障返回 503，已建立会话仍保存在 PostgreSQL。`/me` 不新增 Redis 调用；服务本身已经装载且数据库可用时应继续按现行契约工作。插件整体重启期间的入口中断另按切换窗口处理，不能承诺零停机。

客户端超时可能发生在 Redis 已消费计数之后。建议保留“可能已计数”的结果，当前请求按基础设施失败处理；不自动重放 consume，不将失败业务请求或认证写入自动重试。客户端离线队列、重连后的命令重放及关闭行为须核对实际库配置，不能让命令在切换结束后再次落入旧后端。

## 6. 迁移、回退与故障恢复

### 6.1 数据分类与切换约束

| 对象                | 本期处理                                                                    | 禁止推导                                                       |
| ------------------- | --------------------------------------------------------------------------- | -------------------------------------------------------------- |
| 用户、凭据、会话    | 保留原 PostgreSQL 数据、认证 secret、cookie 和原过期时间                    | 不导出到 Redis，不要求所有用户重新登录，不恢复已撤销会话       |
| PostgreSQL 限流计数 | 保留表与已有数据；切换后停止使用旧计数路径，按已确认策略结束有效窗口        | 停止使用不等于可立即删表，也不意味着旧计数可在任意时间安全复用 |
| Redis 计数          | 仅在隔离、已确认的运行命名空间写入；正常服务重载复用同一状态                | 不通过每次启动更换前缀清空限额；命名空间不隔离实例级淘汰策略   |
| 认证迁移工具        | 继续服务 PostgreSQL 模型；运行时启用 Redis 不应使现有迁移命令要求连接 Redis | 不为计数适配隐式删除库管理的表或改变认证迁移含义               |

### 6.2 首期建议：受控暂停后切换

候选采用单实例下的受控暂停方案，以避免实时双写和跨存储事务；需要负责人接受受影响入口的中断。若要求无中断且计数连续，必须先重开该方案范围，不能在实现时临时补双写。

设 `W` 为所有已开放、实际受限路径的最大有效窗口。R0 必须列出完整规则，确定 `W`、时钟误差余量和在途处理时限；不能只根据登录的 60 秒推断全部窗口。

1. **准备。** 固定待切换候选、旧版本与配置，核对 Redis 版本、凭据、容量、淘汰/持久化策略及隔离资源，备份需要的 PostgreSQL 数据。确认相同数据库和 secret 下的已有账号与会话可用。显式确认受影响入口、中断预算及操作者。
2. **阻止新计数请求。** 通过已确认的部署入口暂停所有会进入认证限流器的请求，并返回约定的维护响应；同时等待在途请求完成或进入可判定状态。迁移门控方式在 R0 明确，不默认新增运行时开关或管理 API。
3. **等待旧窗口结束。** 从确认旧后端不再可能消费计数的时刻起等待至少 `W` 加误差余量，确保不存在离线重放、后台写入或仍在服务的旧进程。无法确定该时刻则保持暂停，不能声称计数已安全失效。
4. **启用 Redis。** 在暂停期间启动选定 Redis 后端的候选，核对装载、账号和会话，使用受控来源验证额度及响应。测试计数与真实计数隔离；不清空其他服务数据，不让新旧后端同时接受同一流量。
5. **恢复与观察。** 满足验收后恢复入口，观察 429/503、Redis 错误、键数量和资源使用，以及 PostgreSQL 限流访问是否停止。保留切换时间、实际中断、验证和异常事实；异常按回退步骤处理。

没有存量计数的全新隔离环境可直接验证 Redis，但不能用该结果证明已有部署的切换。超出已接受中断预算、存在未知写入或证据不完整时，不恢复业务流量。

### 6.3 回退及状态丢失

- **计划回退：** 再次暂停受限入口，停止 Redis 消费并排清在途及潜在重放，从最后可能消费时刻等待同样的 `W` 与余量，再启动原数据库后端。核对原表、原会话和规则后恢复；旧 PostgreSQL 计数应已超过窗口，不能未经核对直接带回有效额度。
- **Redis 运行中故障：** 先按 RL-06 拒绝受影响请求，不自动切回数据库。若计数完整性可证明且未更换状态来源，恢复连接后核对原窗口；若计数丢失、部分恢复或完整性未知，按受控暂停方案恢复，不能立即把缺键当新额度。自动重连成功本身不是完整性证明；R0 必须明确暂停入口的责任、可取得的完整性依据及解除条件，首期可采用停止认证实例并人工恢复的最小方式。
- **Redis 重启或恢复备份：** 普通服务重载且 Redis 状态保留时验证额度持续有效；Redis 数据丢失另测。RDB/AOF 策略、允许丢失及恢复条件需明确，旧备份不自动代表连续计数。[Redis 持久化](https://redis.io/docs/latest/operate/oss_and_stack/management/persistence/)
- **容量与淘汰：** 缓存类淘汰可能重置限额；选择 noeviction 仍可能因内存不足写入失败，须按故障处理并验证恢复。[Redis 淘汰策略](https://redis.io/docs/latest/develop/reference/eviction/)
- **清理：** 本期保留旧限流表及回退所需代码。只有后续明确结束回退期、确认模型与迁移影响并获授权，才讨论清理；不将删除作为本期完成条件。

### 8.4 后续业务缓存的文档变化判据

假设后续已建立的项目业务需要查询缓存，具体缓存需求仍须单独明确。下面检验资料归属，不把该业务加入本期实施范围。

| 后续变化                                             | 应更新的资料                                                                                                                                            | 保持稳定的资料                                                           |
| ---------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------ |
| 复用现有 Redis 公共契约，新增业务缓存                | 该业务已有 PRD 的目标/验收与执行安排；独立新目标才新建 PRD。采用后在业务现行规范明确权威数据、缓存键/TTL、失效、授权及回源。新 PRD 才新增注册与任务导航 | 公共 Redis 规范、认证规范、本 PRD 及原接受事实无需因“多一个消费者”而重写 |
| 消费者提出新的公共能力，或公共版本/配置/生命周期改变 | 在本次需求解释影响；公共 Redis 规范只更新实际变化，补受影响消费者的回归及必要模块边界检查                                                               | 无关业务 PRD、无关规范和旧接受记录不跟随批量改写                         |
| 业务选择不同缓存/故障策略，公共契约已支持            | 该业务自己的现行契约及验证，引用公共规则                                                                                                                | 不把认证的 503、计数保留、迁移窗口复制为全项目缓存规则                   |
| 实现已接受                                           | 按该 PRD 的稳定成果键登记本次接受，保留旧接受各自的候选边界                                                                                             | 不搬迁 PRD，不将需求正文变成所有消费者的长期公共规范                     |

反例：认证计数使用 noeviction，而新缓存希望采用 LRU 淘汰。两者共享一个实例时，键前缀不能隔离实例级淘汰策略；不能只在业务 PRD 写“使用 Redis 缓存”就认定无公共影响。需要明确资源隔离或相容策略，并验证限流保护和容量影响。相反，公共资源和契约足够承载的新消费者，不应被迫重开认证 PRD。

这里的持续治理判据是：相同公共事实只有一个现行维护位置，变更集中于实际受影响的职责，公共变更能够触发相关消费者验证。资料登记、可达性、候选绑定可由现有工具检查；“复用是否合理、是否重复契约、是否遗漏业务失效语义”仍需实际审阅。场景推演支持该结构设计，但不构成多轮长期运行效果已被证明。
