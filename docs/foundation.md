# 插件服务底座

## 本阶段目标与来源

2026-11-05 项目决定：使用 TypeScript，通过 DeepSeek Harness（DSH）插件承接后续 AI 漫剧业务；插件服务独立部署，独立前端通过服务端口调用。当前只初始化基础护栏与最小可运行插件，不以旧 Python 行为替代业务需求。

本次授权包含工程与护栏文件、依赖安装、本地验证。完成边界是：可构建的插件产物通过官方 DSH Profile 装载，提供最小服务探针和受保护的能力查询；权限、结构和文档约束有真实正反例。没有推送、发布或生产操作。

本阶段不提供对话 API、流式事件、生成任务、数据库、前端、SaaS 多租户或模型调用。上次讨论的会话、重连、取消与业务资源授权是后续接口设计的验收维度；在这些入口实现前不标记为完成。

## 结构决定

| 对象           | 决定       | 理由和边界                                                                                 |
| -------------- | ---------- | ------------------------------------------------------------------------------------------ |
| 官方 DSH       | reuse      | 使用已发布 `0.2.2-rc.1`；参考源码提交 `66491b05e3f05ad35bcdd4f6cd7ed26041d9e3db`，不改上游 |
| mio 插件包     | create     | 单个 ESM TS 包，使用 Profile/Bundle 装载；不维护第二套 Agent 循环                          |
| HTTP 处理      | create     | 产品接口只处理本阶段探针、鉴权与能力查询；DSH 路由适配集中于插件入口                       |
| 业务模块       | unresolved | 等具体业务需求后确定模块与数据归属，不创建空层                                             |
| 会话与生成任务 | unresolved | 后续明确身份、入队回执、事件、取消与恢复契约后再实现                                       |

运行时导入方向：插件入口 → HTTP 处理与契约；HTTP 处理 → 契约。只有插件入口可以导入 DSH/Cordis。测试可使用公开 DSH API 验证集成；运行时不得导入测试与开发脚本。跨包只使用发布的接口，不导入上游源码或其内部产物。

运行实例使用显式、独立的 `DSH_HOME`。当前 Profile 只装配 HTTP、工具注册和原生执行器等必要服务，没有模型适配器、文件工具、Shell、MCP 或动态插件管理工具；注册执行守卫拒绝全部工具。以后新增允许工具时必须同时定义输入、授权与副作用验收，不能仅增加工具名称。

2026-11-06 团队采用 [任务协调协议](coordination.md) 和 [记录命令](work-records.md)。每位成员开发时维护自己的 `.work`，公共协议与工具随仓库交付；这是团队共同要求，不依赖个人技能安装。任务协调位于 `scripts/harness/work/`，与工程护栏同属 `scripts/harness/`；Profile、启动和产物 smoke 位于 `scripts/service/`。两者分别声明为 development 源码根及允许依赖，不得被运行时导入。其格式、类型、lint、源码盘点和行为测试进入现有统一检查；不新增运行时服务或依赖。

公共检查仍不要求任何成员的私人记录存在；本地协调记录由 `pnpm work check <task>` 显式检查。源码盘点区分生产、测试、开发脚本、配置、文档与生成/运行资料；遇到未识别文件明确报错，由修改者登记真实归属。该检查不能证明业务职责合理，也不是秘密内容扫描器。

使用 Agent 编码时，用户给出目标与决定，当前 Agent 负责把公共 PRD／相关规格拆解为当前子任务，并自动维护本人的执行目录。仓库内 ensure 按文档与稳定子任务键生成／复用记录和初始模板；update 以整份记录 revision 更新契约及进度，保留候选、原件和恢复保护。旧 v1 记录兼容，交接保留需求关联但不继承授权／通过。此协议不要求用户执行命令或安装 Skills；CLI 不理解需求、不自主调度，Agent 仍须核对来源、范围与授权。

开发模块的 `developmentDependencies` 按源码根声明：护栏／任务协调只导入 `scripts/harness/` 内部模块，服务工具只导入 `scripts/service/` 内部模块；总检查入口可组合各自命令。开发角色不等于职责边界，缺少开发模块依赖声明、越界类型／值导入导出、别名解析后的越界、未明确的动态目标和模块内循环都会报告错误。新增脚本须进入明确职责根，不能在宽泛 scripts 根静默取得权限。未采用运行时反射或进程沙箱作为静态依赖证明。

正文按 `guide <action>`／`context <task> <action>` 输出共同规则与当前动作；记录摘要不含旧 notes、完整 checkpoint 或原始日志。动作章节由 Markdown AST 定位，缺失或重复章节显式报错；文件内示例的代码围栏不构成导航标题。固定公共策略仍参与完整文件摘要，正文加载与完整性核对分开。该入口使按需取用可执行，不能强制任意宿主或执行者永远不读取全文。

已登记的 TS 文件还必须进入类型检查配置；生产 TS 必须同时进入构建配置。新增根目录仅登记归属不足以通过，检查器会对账编译器实际匹配的文件集合。

体量统计来自 TypeScript AST：物理行数（含注释/空行）、函数声明跨度、语法块嵌套深度、if/循环/case/catch/条件表达式节点数。`decisionNodes` 是文件级分支信号，不是完整圈复杂度或算法复杂度；职责聚合、时间/空间成本由相关变更审阅。配置/文档/生成文件不计入业务源码指标。依赖声明采用 `skipLibCheck`，严格类型检查覆盖本项目；第三方声明内部仍由依赖兼容与装载测试补充。

AST 入口为 `scripts/harness/check-source.ts`：通过 TypeScript Compiler API 提取静态导入、导出、`import type`、字面量动态导入/require，并调用模块解析器建立项目内依赖边。框架入口限制、运行时不得依赖开发脚本、未解析的相对导入、已识别的循环、未进入类型检查/构建的源码返回非零；未知/未分类文件由盘点入口阻断。不支持的源码类型显式报告，不降级成文本猜测。该检查不提供完整的数据流分析、任意运行时反射目标追踪或进程安全沙箱；`pnpm typecheck` 和 `pnpm lint` 仍独立执行。

DSH 边界同时核对导入名称、解析器的 `packageId` 和解析目标真实路径向上最近具名 `package.json` 的包名，任一身份指向框架包即受限制。没有 `name` 或 `name` 为空字符串的子目录元数据继续向上查询；遇到最近非空包名即确定归属，遇到 `node_modules` 目录或文件系统根则终止查询，避免把匿名嵌套依赖归到外层包。框架身份由包元数据认定，`node_modules` 只作为查询边界，不按安装目录名称或 pnpm 布局猜测身份。`paths` 别名可能缺少解析器包身份，文件级符号链接也可能保留外层包身份，因此真实目标始终参与判定。已有包元数据读取／解析异常返回失败。生产代码中只有 `src/plugin.ts` 可访问框架包，普通本地别名与其他包保持可用；已有 import／require 条件解析和开发模块隔离继续生效。

最小维护验证：使用已有 guardrail fixtures 验证合法同模块新文件、类型导入越过框架边界、运行时依赖脚本、循环、新增根目录漏编译，以及长而低分支函数仅报告。改变 AST 支持或边界判定时再补对应样例，不以文档包含“AST”或规则 ID 代替行为验证。语言、代码形态与职责由各自适合的检查负责，不把分支数当作算法优劣。

DESIGN-OVER-001 的例外保留真实故障、兼容、权限与恢复依据。是否拆分不能仅凭体量，是否新增抽象也不能仅凭“将来可能复用”；把判断写在本次已有方案或审阅结论中，不另建一份持续台账。该规则持续由项目 `AGENTS.md` 和本节维护，普通检查不读取个人技能安装目录。

QUALITY-01 将已有审阅要求接入任务验收，补上“没有登记审查项也能交付”的缺口。通过护栏配置中的源码范围和显式 `.ts` 路径保守触发，包含开发工具、测试、计划新增路径和删除最后一个源文件；不另维护可被 sync 覆盖的语义 diff 基线。纯格式的源码任务仍需说明不适用理由，文档任务的只读源码 inputs 不触发。代价是源码范围过宽时多一次适用性判断，执行者应声明真实范围。

实现归属 `scripts/harness/work/quality-review.ts`，复用已有 Markdown AST 元数据解析、候选与证据存储。新增任务和显式 update 补入标准，旧记录只读不迁移；缺项需显式对账，旧通过不重新绑定。三维原件防止漏项和把 fail／pending 标成 pass，候选字段防止把旧报告直接登记为新候选。维护验证通过真实 CLI 覆盖源代码／文档范围、旧记录、缺证、失败／待确认、完整原件及候选变化。公共 CI 运行协议测试，仍不读取个人 `.work`，也不能证明所有协作者已执行真实审查。此机制不增加模型依赖或后台调度；人类接受保持独立。

工具链采用 TS 编译器解析源码、ESLint 和 Prettier，以及 Vitest 执行行为测试。文档用 CommonMark 解析器核对本地链接；不复制个人 Python 模板，从而保持项目开发检查只需 Node 工具链。DSH CLI 的传递依赖较多，安装依赖不意味着 Profile 已装载这些能力。锁定 `@opentelemetry/api` 为 `1.9.0` 以匹配本次 DSH 所带 OTel SDK 的 peer 范围；升级时复核该 override。

## 验收与限制

- 核心：格式、类型、lint、护栏、测试、构建均成功；打包产物通过官方 `dsh --profile mio` 启动；受保护查询可用；正常停止后同一端口可再次绑定。
- 必要保障：缺少认证配置不可就绪；错误凭据、未知路径/方法与不允许的 Origin 被拒绝；真实工具函数在守卫下不执行；插件卸载撤销路由与守卫；结构/文档违规样例返回非零。
- 环境：Node 24（至少 24.9）、pnpm 固定版本、隔离的临时 DSH_HOME；没有生产数据、真实模型或收费供应商。源码导出可运行检查，Git 索引检查仅在 Git 仓库中有效。
- CI 文件只代表已接入配置；没有远端运行和分支保护证据时，不声称远端门禁已生效。

当前验收标准见 [验收入口](acceptance.md)，已接受的任务交付通过 [任务索引](tasks/index.md) 定位。个人执行状态、每轮结果及原件在各自 .work 维护，不在公共文档按日期追加。接口状态见 [API 约定](api.md)，日常命令见 [README](../README.md)。

正常任务读取根入口与受影响契约，运行相关检查。只有 DSH 升级、接口/权限/持久化边界变化、模块归属变化或现有护栏漏检时更新对应部分。业务需求明确后追加实际规则，不重新初始化整套护栏。
