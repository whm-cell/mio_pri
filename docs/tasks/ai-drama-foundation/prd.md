# AI 漫剧技术底座建设与护栏验证 PRD（讨论草案）

状态：保留已接受基础与历史架构方向。当前仓库已明确为后端 service，近期候选工作按独立的[后端对话服务 PRD](../conversation-service/prd.md)推进；本页项目、素材与生成安排是未来业务候选，不是当前下一步或对话前置。既有接受事实与其限制保持不变。

需求来源：项目负责人将“垂直链路”定义为 AI 漫剧背景下从 DB、基础组件、业务层到服务层的技术架构、组件/函数预设与护栏治理，并要求通过 PRD、C0/C1 和阶段子任务组织后续工作。现有能力依据见 [底座规格](../../foundation.md)；草案不代表这些候选能力已经实现或接受。

## 1. 摘要

拟建设能够支撑后续 AI 漫剧需求的跨层技术底座：明确职责、数据与调用契约、可复用组件、必要实现与扩展方式，并把采用的架构约定接入现有护栏。

本 PRD 同时追踪两个结果：底座在代表性技术场景中有效；现有护栏在真实建设任务中能够约束实施、识别违规、保存匹配证据并支持续接。具体创作功能和完整产品体验不属于本草案。

### 为什么现在可以编制

PRD 是可追溯的需求来源，不是使用编排能力的唯一文件名。当前项目的 `ensure` 接受公共 PRD 或相关规格，并通过 source、section、key 关联任务。现有 `docs/foundation.md` 可作为本轮分析来源。

需要建设的是一份技术底座需求，而不是为了满足工具形式补造完整漫剧功能。PRD 说明能力和可观察结果，架构方案记录选型、接口和实现理由，任务记录保存本次执行事实。

## 2. 使用者与决策责任

- 直接使用者：维护该项目的开发者、编码 Agent、审查与测试人员。
- 间接受益者：未来 AI 漫剧产品的创作者；本轮不承诺尚未定义的用户功能。
- 用户决定：建设目标、阶段边界、数据/权限/外部副作用承诺、风险取舍和最终接受。
- Agent 负责：根据确认来源提出拆解、方案、检查方法并执行获授权工作；不能把建议或测试通过写成人类接受。
- 不虚构人员姓名、访谈、市场规模或交付日期。

## 3. 背景与当前基线

### 已确认目标

1. 产品方向是 AI 漫剧；本轮关注技术架构和公共能力。
2. 必须结合现有护栏推进，并验证护栏在此类真实任务中的效果。
3. DB、基础组件、业务、服务与治理之间的责任和契约属于分析范围。
4. 历史产品方向为单人登录后创建项目并生成，后续需要团队协作；当前已收敛为先积累后端公共能力，不在本期实现项目、素材或生成，也不以项目 CRUD 作为对话前置。多租户仍不在本期范围。
5. 首期单实例服务，先跑通本地及单机部署。
6. Mio 自己提供完整登录底座，允许用户自助注册；首期注册即可登录，邮箱验证后续接入。以上方向来自项目负责人明确回答。

### 当前项目事实

- TypeScript 插件服务，经固定版本 DSH 公开插件接口接入；DSH/Cordis 依赖集中于适配入口。
- 原有 HTTP 探针、服务凭据和能力查询保留；账号认证已有指定候选的接受，配置与验证边界见 [认证底座](../../auth.md)。当前 Profile 仍不授权模型工具。
- 已有 AST 边界、源码覆盖、统一检查、个人任务记录、候选证据与交付流程。
- 已接入 quality-review 的登记和原件校验；实际语义审查由 Agent/审查者执行。
- 认证持久化使用 PostgreSQL；项目/素材业务数据、生成任务、媒体持久化和对话服务尚未实现。本仓库不包含前端 UI。
- 已有开发接受事实统一见[本 PRD 成果入口](complete/report.md)，不在需求页复述受验候选和运行结果。

## 4. 目标、范围与成功标准

### 目标

- 后续开发能够找到明确的模块入口、数据所有者和可复用能力。
- 采用的公共组件有清晰契约与可执行消费者，避免空层和预设后无人使用的函数。
- 代表性跨层场景验证数据、错误、身份、版本及外部副作用语义。
- 已采用护栏能够拒绝对应违规，合法使用保持可用。
- 每个交付子任务可由来源追溯到候选、证据及接受结果。

### 范围建议

当前目标包括架构分析、选型依据、数据和组件契约、必要参考实现、相应护栏及验证。实际实现必须以阶段范围和授权为准。

完整创作工作流、产品 UI、商业计费、生产部署、全量业务表、任意供应商支持、通用工作流平台不自动进入当前范围。用户将来明确需要时另行评估，不列为默认后续任务。

### 可观察的成功标准（待采纳）

1. 每项当前采用需求能关联到职责/契约、实施子任务与相应验收；没有只靠目录名称认定完成的能力。
2. 每项当前采用公共组件有实际职责消费者或明确的外部消费契约，并有正反例或审阅依据；不设“必须两个调用方”的机械阈值。
3. 代表性场景经约定入口访问实际被测组件；持久化行为使用隔离的真实存储实现验证，外部模型可用明确标注的模拟适配器。
4. 对应护栏有合法与违规对照；记录命令、实际退出/状态、候选和环境。通过模拟供应商不等于验证真实供应商。
5. 所有必需验收都属于同一有效候选；不完整保持 pending，真实接受前不进入 complete。
6. 数量、时延、吞吐或可用性目标只有取得负载依据并确认后才成为门槛。

## 5. 使用场景与验证边界

这些场景用于检验架构，不替代具体功能 PRD，也不承诺当前已经具备这些能力。

| 场景候选                               | 要回答的架构问题                                 | 需真实参与的边界                           |
| -------------------------------------- | ------------------------------------------------ | ------------------------------------------ |
| 一个项目资源的读取、版本更新与重新打开 | 归属、版本冲突、事务、服务与数据访问如何合作     | 服务入口、应用/业务、数据访问、隔离 DB     |
| 一个素材引用的保存、访问与失效处理     | 元数据与文件归谁、引用怎样稳定、部分失败如何处理 | 业务服务、资产组件、存储适配和元数据       |
| 一次有外部回执的生成操作               | 请求身份、状态、重复回执、结果未知和恢复由谁处理 | 入口、应用服务、任务记录、受控供应商模拟器 |

这些是未来业务验证候选，须在对应业务目标被选择后才展开，不构成当前开发单元或对话服务依赖。场景数量不作为质量指标；无需完成一部漫剧才能判断数据库或任务恢复约定是否有效。

## 6. 价值与验收的两条线

### 技术底座验收

验证组件之间能否按确认契约协作，实际数据能否正确保存/恢复，错误与副作用是否保持语义。业务层面的价值是为后续漫剧开发提供真实可用的支撑；本阶段不验证画面质量或完整创作体验。

### 护栏能力验收

验证规则在实际工作中是否生效：不仅检查有文件、有字段，也验证合法行为通过、违规被拒绝、假通过无法成为交付证据。

两条线可以共享原始证据，但结论分别写。`pnpm check` 成功、quality-review 原件格式正确或任务标为 ready，都不能替代架构行为的验证。

### 7.2 需求与实现方案分开

需求示例：并发提交旧版本更新时必须给出可识别冲突，不能静默覆盖新版本。

方案候选：使用条件更新、数据库版本列及应用层错误映射。是否采用某 ORM、列名或封装类，不应先写成需求。

每项组件预设记录：职责、真实消费方、输入/输出、身份与生命周期、错误、副作用、最小替代、验证入口。只有已采用边界创建必要模块；未决能力保留候选，不生成一套空 BaseService/BaseRepository/utils。

### 7.3 标准子任务卡

执行任务使用[协调协议的拆解方法](../../coordination.md#从需求形成执行任务)与[现有记录字段](../../work-records.md#创建任务)，不另造卡片格式。本需求额外关注实际组件消费者、跨层数据语义，以及技术行为与护栏效果两条验收线。

例：`persist-resource-version` 只在 DATA-01 被采用且资源归属和冲突语义明确后建立。C0 确定责任/事务/错误约定；C1 实现与测试；陈旧版本更新被拒绝、原记录可重新打开，才构成行为证据。代码型 scope 会沿现有规则自动带入 quality-review。

### 7.4 护栏验证矩阵

| 被验证能力       | 合法行为                        | 对照/异常                                                                 | 证据边界                                              |
| ---------------- | ------------------------------- | ------------------------------------------------------------------------- | ----------------------------------------------------- |
| 来源与拆解       | 子任务能追溯公共章节和目标      | 没有确认的候选被提出为实施范围时，Agent 应保持候选                        | 工具只能检查结构；语义需审查                          |
| AST 与源码覆盖   | 合法依赖与新源码进入检查        | 越界导入、别名绕过、漏编译、非法运行依赖被拒绝                            | 隔离 fixtures 中执行，不破坏主工作区                  |
| 数据/组件契约    | 约定操作和消费者正确运行        | 越权、陈旧版本、部分失败、错误返回符合契约                                | 必须经过实际被测组件                                  |
| quality-review   | 有依据地审查算法、unused、reuse | 已植入明确问题被指出；合法框架入口/必要一次性适配不误报，证据不足保持未知 | 语义能力需审查者实际阅读；不能用模板字段填满替代      |
| 候选与原件       | 当前候选匹配原件                | 改代码、改验收、损坏原件、复用旧报告不能满足新候选                        | work check/evidence/deliver 的真实结果                |
| 按动作读取与续接 | status/context 恢复当前步骤     | 无关历史不默认展开，中断后不重复创建任务或继承过时授权                    | 实际运行的返回内容和操作记录                          |
| 交付与重开       | 匹配证据和真实接受后发布报告    | 缺证、无接受或新候选不得 complete；重开保留旧报告                         | 自动恢复/拒绝测试在隔离样例；真实用户任务绝不伪造接受 |

治理随各阶段落实，阶段末再做贯通对账。不为了执行每个命令而制造虚假交接、失败、角色或接受；完整指本阶段适用义务都有验证。

## 8. 阶段、C0/C1 与交付
