# 团队任务协调协议

2026-11-06 项目负责人明确采用：团队每位成员拥有自己的 `.work`，协调能力随项目交付，无个人 Skills 时也能执行。根 [开发入口](../AGENTS.md) 负责发现协议，本页负责判断和流程，[记录和命令](work-records.md) 负责数据与 CLI；工程约束继续由 [底座规格](foundation.md) 维护。

## 执行者、归属与入口

开发者或当前 Agent 是执行者。收到目标或“继续”时，按下表直接选择动作，沿同一任务推进；用户无需指定工具或重复授权。文档提供判断协议，命令核对可确定的事实；没有执行者或明确接入的命令，目录本身不会自动运转。

| 当前情况               | 执行者的动作                                                                       | 输出和停止条件                                           |
| ---------------------- | ---------------------------------------------------------------------------------- | -------------------------------------------------------- |
| 新成员／新工作区       | `work init`，阅读根入口、当前需求和相关子文档                                      | 本人独立的本地记录；已有证据保留                         |
| 新任务或讨论           | 明确结果、范围、非目标、授权、验收、下一步；`work start` 建立同一任务记录          | 仅分析的授权只做分析；影响范围的未知只暂停依赖动作       |
| 继续／中断恢复         | `work status` 找任务，读取记录、声明的来源与证据；`work check` 对照当前现场        | 历史记录不自动成为指令；定位最小已授权下一步             |
| 需求或技术判断尚未解决 | 对比有意义的候选，以失败场景、证据、成本和最小验证作判断                           | 区分事实、提案、已确认决策与阻塞未知；不擅自确认业务取舍 |
| 已授权实现             | 核对契约和依赖，必要时 `work sync`，执行最小完整修改                               | 保留既有保护和无关改动，执行相关验证                     |
| 候选或证据变化         | 核对受影响文档与任务；更新同一记录，`work sync`；通过 `work run/evidence` 收集结果 | 新候选只使用匹配的证据，原失败保留                       |
| 交接／换工作区         | 准备 `work handoff`，核对代码、共享任务来源与必要证据的实际取得方式                | 接收方 `work receive` 核对文件，再确认本地授权和依赖     |
| 完成／取消／暂缓       | 对照验收和人类结果决定当前状态；按需 `work archive`                                | 不自动接下一功能，不删除旧证据，不擅自提交、推送或部署   |

同事可以用任意支持文件与命令的开发工具。没有自动化 Agent 时，开发者按同一协议操作。独立审查、浏览器或远端能力不可用时，记录缺口；普通自检不能冒充独立审查、真实业务验收或远端通过。

| 事实                                       | 权威位置                                     | 本地记录的作用                               |
| ------------------------------------------ | -------------------------------------------- | -------------------------------------------- |
| 团队规则、需求、接口与验收标准             | 本仓库公共文档或项目明确的共享来源           | `sources` 引用实际文件和版本；不另立需求     |
| 每人的执行进度、下一步、原始日志           | 该成员工作区的任务记录                       | 单任务单写入者，多个任务各自独立             |
| 跨人的范围、依赖、写入归属、候选与交付结论 | 已有共享计划、Issue／PR 或明确的共享交接文档 | `sharedRef` 指向同一来源；交接只发布必要事实 |
| 人类确认、验收结果、操作授权               | 实际人类指令及受其约束的共享契约             | 区分确认与提案；本地标签不能自行授权         |

没有共享渠道时先在仓库公共文档保存必要的脱敏协作事实；仅在本机 `.work` 写“已交接”不能视作同事已取得材料。不自动创建远端、上传日志或覆盖他人目录。相同任务在不同成员处可沿用同一任务 ID，但各自维护本地执行事实；共同契约仍只有一个权威来源。

## 目标、拆解与协作

开始前记录最小完成约定：目标、允许写入的 `scope`、只读依赖 `inputs`、相关需求与子文档 `sources`、非目标、真实授权、验收条目、下一步和停止条件。简单修改只需一个小记录；多阶段工作只细化当前可执行切片，不预造所有后续任务和审批角色。

需求层级沿公共来源读取：根入口 → 当前目标 → 受影响的详细规格／API／验收子文档。引用目录页不表示已经读过其全部内容；把本任务实际遵循的子文档逐个登记在 `sources`。链接目标调整、子文档新增或契约变化后，重新核对来源列表。脚本比较已登记文件的字节变化，不推断业务语义或自动发现所有遗漏的阅读依赖。

分解只到下一项任务的输入、输出、依赖与验收已足够执行。技术选型先说明使用条件，再比较候选和最小验证；不从现有代码倒推需求。规划达到可执行条件就停止，无关未知不阻塞当前切片。

多人或多个执行者协作时，在共享交接明确各任务的范围和所依赖的固定候选。独立记录不是代码隔离：同一文件、公共契约、持久化或权限边界存在写入冲突时，先由一个集成责任人统一契约，串行修改或隔离 checkout/worktree。不要给尚未结束的同一写入范围再安排执行者。

依赖条目记录任务、团队可访问的来源和实际就绪情况。执行者实际检查后才能把 `ready` 改为 `true`；脚本不联系其他成员、查询远端或把私人进度当作共享调度。跨工作区开始前先选择主干、固定上游提交或明确范围的未提交快照；分支名和聊天摘要不能代替可取得的代码。

## 状态、证据与接受

任务草稿 `stage: null` 表示契约尚未就绪。契约完整并执行 `work sync` 后可进入 `C0_READY`。分阶段工作采用以下含义；执行者依据实际行为更新记录，脚本不替代判断：

| 状态                  | 含义                                   | 必须保留的依据                                                                   |
| --------------------- | -------------------------------------- | -------------------------------------------------------------------------------- |
| `C0_READY`            | 当前切片范围、授权、依赖和验收足够开始 | 人类目标与契约、基线和下一步                                                     |
| `C1_IMPLEMENTATION`   | 在授权范围内实施或修复                 | 实际差异和未完成项                                                               |
| `C1_EVIDENCE_PENDING` | 有候选，证据或结果接受尚未完成         | 同候选的检查、审查、业务观察和缺口                                               |
| `C1_RELEASED`         | 此切片的所需证据齐备且人类已接受       | 每项验收匹配的通过证据、`reviewDecision: ACCEPT`、`releaseDisposition: RELEASED` |

实现中的真实故障在已授权修复范围内直接修复再验证。只读审阅发现缺口时报告缺口，不把审阅请求当成修复授权。需要新的人类取舍时，只暂停依赖该取舍的动作；清晰的现有授权不要求重复确认。`C1_RELEASED` 仅表示记录中的切片完成，不授予发布、外部写入或下一阶段权限。

编码前由人类目标推导验收条目，每项有稳定 ID、可观察结果和验证方法：`automated`、`review` 或 `behavior`。当前负责人的明确指令是目标和操作范围的确认来源。Agent 可提出拆解与测试，但不能把提案写成已确认需求，不能降低阈值。影响公共契约、权限、数据或外部副作用的未决事项记录为 `OPEN` 并阻塞依赖动作。

`work run` 直接运行明确的命令参数，保存独立日志、退出码、候选和 Node/平台环境；比较执行前后的内容，并核对已有输入文件和源目录的身份、修改／变更时间，发现写入再恢复也不能算作通过。这个核对依赖文件系统的元数据，不是进程沙箱或任意中间行为追踪；执行者仍须确认命令实际检验了声明的输入。`work evidence` 登记已实际取得的审查／业务观察及其原件。观察还应在原件中说明操作者、场景、操作、环境、实际结果、限制；需要独立性时记录实际独立执行者。缺少所需工具或原件就保持 pending。

自动检查、代码审查、业务验收和人类接受分别判定。涉及状态、恢复、权限、跨模块生命周期或重要共享契约的实质修改，应由未实施该候选的审查者审查真实差异，并验证触发、约束、失败路径与更小替代；能力缺失时明确独立审查缺口。校验器能发现结构、候选和原件不一致，不能证明人工观察诚实或人类确认真实。

## 变更同步和恢复

执行前和交接前检查：当前人类意图、记录归属、仓库／分支、实际差异、候选、需求来源、证据环境和下一步。`work check` 返回变化与缺口且不修改记录。

遇到变化先查看实际 diff 和新文档，判断哪些规则、输入、验收或授权受影响，更新记录与受影响的共享文档，再 `work sync <task> "实际核对结论"`。该命令更新检查点并保留全部旧证据；旧候选的通过不会自动迁移。任务契约和声明文件相同的分支／HEAD 变化，经核对同步后可继续使用同一内容候选的证据。

快照按登记文件与任务契约绑定；粒度是整文件，相关文件修改后需重新验证受影响条目。未受影响证据可以人工论证复用，但目前命令不会自动重新绑定旧证据，原件和复用理由必须可审阅。原始失败不能用新成功覆盖。候选变化会撤回本地释放结论，重新等待证据与接受。

中断或记录缺失时，从公共需求、共享交接、源码和测试恢复事实，不能把“没有记录”推断成未实现或已完成。确认基线、差异、授权后建立本人记录并核对。归档记录只提供历史；需要继续时显式取消其 `archived` 标记并重新核对授权、候选和下一步。

证据缺失或损坏只影响依赖它的完成判断；其他已授权工作可继续。显式 `work run/evidence` 可在旧释放证据失效后补证，保存新结果时退回待验收并重置人类接受；仍须满足当前授权、依赖和上下文条件。外部副作用结果未知时，保留原请求身份并通过受支持的状态查询核对；不能为补日志重发一次。跨设备应分别核对代码、记录和必要证据，哈希与本地路径本身不传输文件。

## 交接、归档和维护

发送方先核对候选，用 `work handoff` 产生本地 Markdown；审阅脱敏后，将必要内容发布到既有共享来源。交接包含目标／非目标、范围、来源、固定代码候选、依赖、阻塞、已执行结果与限制、下一步、停止条件和必要原件的取得方式。草稿不自动上传任何东西。

接收方取得代码、必要的文档和原件，将共享交接取回本地，再 `work receive`。命令对照实际文件清单，代码不匹配就拒绝创建记录；即使匹配，收到的也是本人草稿：须重新核对本地授权与依赖，原报告的通过不能直接当成本机有效证据。必要原件应实际取回并登记；可以重跑的检查在核对授权后重新执行。公共报告优先放在已有 Issue／PR；避免把包含自身候选标识的交接报告放入同一候选的输入，造成自引用。

任务结束或明确停止时，按需 `work archive` 原地标记历史；不自动删除日志、复制整仓库或按日期清理。日志与截图只保存必要原件，可重建的 fixture 放系统临时目录。没有备份的资料仅本机可用；传输、保留期和清理由实际项目选择决定。

公共 CI 运行 [统一检查](../README.md)，验证协调命令及公共文档；每个人的 `work check` 检查各自记录。CI 无法读取未提交的私人资料，不宣称能证明每个人均已维护记录；共享交付依靠可访问的契约、候选和证据审阅。

## 实现依据与能力边界

| 需要的保证／失败场景                         | 本次机制                                     | 最小替代与代价                                                   |
| -------------------------------------------- | -------------------------------------------- | ---------------------------------------------------------------- |
| 新成员没有个人工具或旧会话，无法知道如何续接 | 仓库入口、本协议和命令说明                   | 只保留私人说明无法满足共同能力；增加两份公共文档，无新增依赖     |
| 重复初始化、别人的目录或错误工作区覆盖记录   | 成员绑定、排他创建、路径与符号链接检查       | 仅约定目录名无法保留原件；身份只是本地标签，不是安全认证         |
| 需求、子文档、代码或验收变化后沿旧状态推进   | 显式输入清单、内容快照和有理由的对账         | 仅比较 HEAD 漏掉未提交内容；每次快照只读所需文件，不保存项目副本 |
| 把过期测试、失败日志或别人的接受当成当前通过 | 候选绑定、独立原件、释放一致性检查           | 纯文字通过无法检查原件；内容哈希有读取成本，不证明业务语义       |
| 交接只传笔记，缺少相应代码和原件             | 可移植交接、接收校验、授权与证据重新核对     | 不建同步服务；材料通过既有协作渠道实际传输                       |
| 多执行者误写同一记录                         | 单任务单写入者；命令结束前检测记录是否被改动 | 不提供分布式锁或并发事务；此检测不能替代写入者协调               |

选择文档协议配合显式命令，是为了同时覆盖判断和可确定的核对。纯文档缺少可复现的候选／原件校验；常驻调度、数据库、自动角色系统没有本次需求依据，增加部署和恢复成本。本机制不联系他人、不自动派发 Agent、不提供全局锁，也不替代运行时的权限或副作用保护。

验收与已知限制维护在 [验收记录](acceptance.md)。新增公共契约、记录格式或命令时，同时更新本页、命令说明与正常／违规／恢复用例；日常任务只更新自己的记录和受影响公共事实。
