# AI 漫剧技术底座：S0 架构基线

需求来源：[技术底座 PRD](prd.md)。本文件保留 S0 设计前提、历史基线的复用理由与后续项目方案。认证切片已有指定候选的接受；当前运行行为以[认证底座](../../auth.md)和[API 规范](../../apis/index.md)为准，接受范围以[成果入口](../complete/prd-5f1fa63bbcbb5049/report.md)为准，不在本页复制运行流水。后续项目与生成目录、接口仍为候选，不能据此认定 S1/S2 整体实现。

## 已确认前提与首期取舍

项目负责人已确认首期单人登录后创建项目并生成，暂不建设多租户，后续需要团队协作；首期运行单实例服务，先验证本地与单机部署。

据此建议采用单插件包中的模块化结构。项目、素材和生成记录以明确身份关联；业务授权集中在应用服务入口，未来增加项目成员策略时沿用项目和资源 ID。首期不预建 tenant、team、角色配置、分布式调度或通用工作流框架。“单人”按项目当前不共享理解，不额外推出全系统只能有一个账号；账号创建方式由登录方案明确。不能从请求体信任 userId，也不能因为单实例忽略并发冲突。

登录方向已确认并已交付指定认证切片：由 Mio 自己提供邮箱/密码自助注册、登录和持久会话，具体行为与限制只维护在认证规范。原设计顺序是先认证、再由项目服务消费可信 userId；有限 auth/HTTP 抽取已有[独立接受成果](../complete/prd-5f1fa63bbcbb5049/report.md#auth-http-shared-primitives)，后续业务候选是项目用例，不能把“先交付认证”继续理解为尚未执行的首项。

## 身份、项目与扩展边界

建议首期的最小概念是可信用户身份、项目、项目内资源；S1 先验证项目记录，不一次性设计剧本/分镜/角色/场景全量表。

- **可信身份**：入口经登录验证得到稳定 userId，再传入应用服务；请求中的项目 ID 只是待访问对象，不能替代授权。客户端不决定 ownerUserId。
- **项目**：具有稳定 ID、创建者/所有者身份及自身修订号。资源通过 projectId 关联项目，避免把用户名或用户目录当作资源主键。
- **首期权限候选**：应用服务对当前可信 userId 与项目所有者做一致检查，数据访问同时以归属条件限定查询/更新；模型工具、HTTP 和未来后台入口均经过该服务。
- **未来团队扩展**：新增成员关系和授权策略，在同一项目身份下解析访问权；不能简单继续把所有查询限定为所有者相等。迁移旧项目成员、权限撤销与正在执行任务的关系要由未来团队需求验收；本期不提前实现。
- **资源修订号与素材历史版本**：修订号用于防止并发覆盖，不能当作完整素材版本树。是否保留历史字节、引用固定版本还是跟随更新，在资产任务确认后再决定。

“未来可扩展”的验收范围是职责不混淆、身份和归属显式、供应商/DB实现不泄漏到业务入口；不承诺未来团队能力零迁移或零改动。

## 数据与事务路线

**当前认证切片采用 PostgreSQL。** 选型比较保留如下，SQLite是比较时的轻量备选。 当前单用户单实例本身不排斥 SQLite；偏向 PostgreSQL 的理由是服务已有独立部署定位、后续确定要团队协作，希望同一迁移与并发验证路径可继续使用。代价是增加数据库进程、备份和运维配置。本轮已为认证锁定 Better Auth 1.7.18 和 pg 8.23.1；没有为未来项目/素材预建 ORM 或通用数据层。

| 候选       | 适合当前目标的收益                                                 | 成本与采用条件                                                                               |
| ---------- | ------------------------------------------------------------------ | -------------------------------------------------------------------------------------------- |
| PostgreSQL | 明确的服务端连接、事务和数据约束；版本条件更新可经真实并发连接验证 | 需要独立数据库环境和迁移入口。首个数据任务固定版本、驱动和隔离测试方式后采用                 |
| SQLite     | 嵌入式持久化、本地设置少，适合单实例初步运行                       | 同一数据库同一时刻只有一个写入者；应测量代表性写入和排队成本，不凭“团队”二字断言它一定不适用 |

PostgreSQL 官方说明并发更新在 Read Committed 下会对更新后的行重新判断 WHERE 条件；这可以支撑 `id + expectedRevision` 的条件更新方案，但不能替代业务授权和零行结果处理。SQLite 官方给出的单写入者限制用于界定比较条件，未在本项目测得容量或延迟。[PostgreSQL 事务隔离](https://www.postgresql.org/docs/current/transaction-iso.html)、[SQLite 适用场景](https://www.sqlite.org/whentouse.html)。

首个数据任务建议直接表达少量明确的存储操作；不为尚未使用的查询引入 ORM 抽象层。当前认证使用库自带的 PostgreSQL 适配和迁移，连接释放与回滚由真实集成验证；后续业务用例的存储端口仍按消费者选择，不照搬认证表模型。

事务由应用用例定义“哪些变化要共同成立”，适配器负责 begin/commit/rollback 与连接释放。单条条件更新已足够时不增加 UnitOfWork；有多个必须一致的写入时用一个明确操作承载，不让调用方手工协调几个提交。

外部生成和文件写入不与数据库天然原子：不跨整个模型调用持有数据库事务。S2 再依据外部协议定义提交记录、结果未知、状态查询、产物写入和记录确认的顺序。没有幂等/查询依据时不自动重发，不能预先声称 exactly-once。对象存储、队列和恢复任务只在这些实际边界需要时加入。

### auth 与基础 HTTP 的复用及护栏改进方案（有限采用）

<a id="auth-http-reuse"></a>

路径常量、共同响应原语、正文局部常量与 helper 模块依赖边界已有限采用，接受范围、候选、证据与限制见[公共原语成果](../complete/prd-5f1fa63bbcbb5049/report.md#auth-http-shared-primitives)，原认证接受保持独立。本节维护取舍与验证设计；现行符号、消费者和协议分别查 [API 公共能力](../../apis/index.md#运行时公共能力)、[认证职责](../../auth.md#职责与限制)及两域 HTTP 契约，不维护第二份 API 表或函数清单。

原认证审查因身份、Cookie、方法和库错误响应的差异保留两个处理器；更小的响应原语抽取与此相容。目标是减少共同响应知识的重复维护，并使后续消费者找到可信身份和响应能力；当时未观察到认证前缀故障或已证实的响应字段漂移，不以假定故障作为收益证明。

| 能力                 | 决定与理由                                                                 | 最小替代与未采用范围                                                                            |
| -------------------- | -------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------- |
| 认证前缀             | 一个权威常量供注册、匹配与库选项使用，减少同步漏改。                       | 一个导出足够，不建路由注册表或全局 constants 文件。                                             |
| 共同响应原语         | 有限抽取共同头与包装错误序列化，替换旧共同逻辑；代价是显式导入与共享契约。 | 成功响应留在处理器；若需大量策略参数或维护成本不降，退回独立实现与逐项审查。                    |
| 正文限制             | 只在认证处理器局部命名单位，读取器保持私有，当前只有认证 POST 消费。       | 不宣称共享能力；新消费者确需相同字节、超时和流清理语义时，再比较共享与局部实现。                |
| 认证配置与库选项     | 保留原归属，运行时和迁移共用，避免第三份配置或表模型。                     | 不增配置服务、迁移框架或 DB 池工厂。                                                            |
| 可信身份             | 保留现有解析能力，未来项目入口传已验证主体，由应用服务判断归属。           | 不额外导出无人消费的 IdentityService；项目任务再确定 userId 或含 sessionId 的窄契约。           |
| 完整处理器和来源校验 | 两个处理器及各自校验保持独立，差异有协议依据。                             | 不建通用 router、统一 CORS/认证策略或成功响应器；局部 Origin 相似不足以合并认证 BASE_URL 约束。 |

抽取只共享响应原语，保留来源检查顺序、方法/路由优先级、CORS/Cookie、204/Content-Type、库原始响应和多 Set-Cookie 转发。不能把允许 Origin 当身份、服务凭据或登录状态当业务归属，或把库错误/限流重新包装成服务错误。正文流清理、会话只验证/刷新与装卸生命周期仍由各自入口承担。

后续业务从现行规范发现能力：HTTP 适配器使用本服务响应原语，取得可信主体后传应用服务；应用服务不依赖 Node HTTP、DSH、认证驱动，也不经 helper 访问数据库。原始响应、流式输出或其他协议按真实差异保留独立实现。公共能力须有明确职责、真实消费者或外部契约，不要求两个调用方，新增测试调用也不能证明空组件有价值。共同字段/头、新业务入口、库升级或响应/来源协议改变时，才重新评估共享粒度。

抽取沿[既有生命周期与质量审查](../../coordination.md#验证与接受)：先说明职责、符号/消费者、身份/错误/副作用差异、最小替代和收益；候选覆盖相关处理器、契约、配置、装配、迁移及测试，verify 核对读取/序列化成本、真实调用和旧逻辑替换。helper 的窄依赖方向用 AST 合法与违规输入验证，包括 type-only、别名与重导出；不声称符号级沙箱或全部 src 已隔离，不修改 quality-review 格式或把相似实现设为机器失败门槛。

共享正文读取器、身份新接口、相似发现工具和自动抽取平台均未采用。只有反复出现搜索遗漏，才评估 AST/符号候选发现的漏报、误报与维护成本；它只输出线索，不自动抽取或阻断。没有此证据时，调用关系搜索和现行规范入口是更小方案。

#### 有界试点与保留缺口

首次有限抽取的验证设计如下，指定候选的实际运行与接受范围仍以成果为准；这些方法不成为每次业务开发的全套门禁。

1. 抽取前经两个真实入口与隔离 DB 建立状态、头、正文、Cookie 和副作用基线，预期来自公开契约及抽取前观察，不导入新常量或 helper 生成预期。UUID 核对服务端生成、头体一致且不沿用客户端值，保留失败与未知。
2. 同判据前后对照成功、包装错误、库错误/限流、204、Content-Type 与来源/路由/方法顺序，确认新原语实际被调用、前缀只有一个来源、旧逻辑已移除。受控多 Set-Cookie/原始字节只证明适配器转发，不证明库在同场景产生多个 Cookie；断流只报告可观察清理，不伪称客户端收到 400。
3. 在隔离 fixture 检验下列六种审阅情形，新 AST 规则另有合法/违规输入，均不修改真实接受。
4. 完成受影响的真实 HTTP/DB、打包装载与统一检查，审阅共同知识是否收敛、调用是否更清楚、维护收益是否大于新增 API/参数成本，不凭行数或未测性能判采用。

| 对照场景       | 判断依据                                                                                                   |
| -------------- | ---------------------------------------------------------------------------------------------------------- |
| 可复用却重写   | 定位已有 helper、重复维护影响与替换位置，仅报相似不足。                                                    |
| 误合并         | 库错误重包装、Set-Cookie 合并或预检策略破坏实际入口断言，说明应保留的协议差异。                            |
| 提取后未使用   | 新导出只有测试调用或处理器仍走旧逻辑时，unused/reuse 判失败；类型通过不能反证。                            |
| 过期入口       | 失效链接由文档检查发现；链接有效但消费者已不用，须由调用链审阅发现。                                       |
| 新业务发现演练 | 未参与者经导航在隔离 HTTP fixture 复用并解释可信主体传递，只证明发现路径，不证明项目、持久化或生成已交付。 |
| 合法独立实现   | 原始库响应、专用读取器或单消费者身份不因相似/调用少而误报，保留理由须有真实协议依据。                      |

首次试点仍披露 **16 KiB 精确边界和 10 秒超时缺少直接断言**；只命名数值时保留原超限/中断回归。未来改变读取器须补分块字节边界、408 和监听器/定时器清理验证，不能因本次抽取宣称缺口已补齐。

停止在最小能力的行为对照、真实消费者、必要依赖正反例与独立审阅齐备；后续复用有效证据，只重验受影响或尚缺证场景。若共享原语持续增加 Cookie/CORS/路由选项、调用方仍绕回旧实现或维护成本未下降，缩减到路径常量、局部命名和审查入口，不继续建设通用平台。静态、回归、净收益、远端 CI、浏览器与生产各按自己的证据判断，本设计和有限接受不证明后续项目/生成能力或生产就绪。

## 首个实现任务候选与验收

本节标题保留原设计锚点；原来的首项认证切片已经接受。下一项候选是 **登录后的项目创建、读取和带修订号更新**，消费现有可信身份，将应用服务→数据访问→真实数据库贯通。认证契约见[认证底座](../../auth.md)，项目业务 API 尚未发布；下表仅列后续项目用例的进入条件与候选验收。

| 环节        | 需要明确／观察的结果                                                                                                                |
| ----------- | ----------------------------------------------------------------------------------------------------------------------------------- |
| C0 进入条件 | 登录产生可信主体；确定项目字段及初期操作；采用的 DB/驱动和迁移方式可运行；确认未授权/不存在/版本冲突的外部语义及 allowed scope      |
| 实现范围    | 消费现有可信身份、项目存储和服务、实际 HTTP 适配、必要迁移与生命周期、对应契约和测试；数据路径只使用隔离实例                        |
| 正常场景    | 登录后创建项目；通过实际入口读取同一 ID；成功更新后修订号改变；重启服务/重新连接后数据仍可读取                                      |
| 权限场景    | 未登录被拒绝；请求体伪造 owner 无效；采用的错误策略下，非所有者不能读取或更改目标。用不同测试主体验证隔离，不以首期个人使用为由省略 |
| 并发场景    | 两个请求用同一旧修订号更新，只能一个成功；另一个得到约定冲突，不能悄悄覆盖新内容                                                    |
| 故障场景    | 必须共同写入的数据在失败时不部分提交；连接、启动失败和关闭处理具有真实观察；未运行的路径保持未验证                                  |
| 护栏场景    | 合法装配/业务端口调用通过；HTTP直接导入DB、领域导入驱动、运行时导入脚本等对应违规被拦截；保持现有 DSH、动态导入和编译覆盖保护       |
| 接受条件    | 同一候选的自动检查、实际入口/DB行为、独立审查与人类接受齐备；不推导素材或生成链路已完成                                             |

项目名称字段范围、版本冲突码等常规细节由实施方案集中说明；认证载体与生命周期由认证底座契约定义，涉及资源权限的取舍必须先确认。删除、转移所有权、共享成员与历史资产清理不进入此首项。

## 护栏增量与后续任务

认证切片的边界依据见[源码护栏](../../engineering/source-guardrails.md)，本设计不再维护另一份现行允许清单。新增项目持久化或存储适配时明确归属、允许依赖和合法/违规用例，按实际影响更新规范与 TypeScript AST 检查，不整体放开 src 的文件访问。

首项若新增生产目录，需要检查 sourceRoots 与模块规则的匹配顺序、类型/构建覆盖及实际打包消费者，避免仅登记目录后漏检。原有 `scripts/harness` 与 `scripts/service` 隔离保留；业务迁移是服务运维入口，不能由通用 guard 隐式执行或读取业务数据库。

后续素材与外部任务只在对应场景前提明确后展开；完整功能 PRD 到来时另行作为独立需求推进。本方案不建立新 PRD 索引或父子关系系统，实施安排统一在[当前 PRD](prd.md#81-阶段建议)。
