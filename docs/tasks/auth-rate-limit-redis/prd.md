# 项目 Redis 接入与首个认证限流切片 PRD

R1 的交付范围、验证与接受从[已接受成果](complete/report.md#auth-rate-limit-redis)核对；本页维护需求、安排和决定。§8.2 的 A/B/C 采用决定与本机实施授权保持，R2 仍未选择，真实环境部署未获授权。R0 的接口探针保留其原有证据边界，不代替 R1 的真实验证。

本 PRD 覆盖项目接入 Redis，以及使用现有认证限流验证首个垂直切片。公共运行能力与认证业务规则属于同一建设目标中的不同职责，不另拆成两份重复 PRD。资料入口见[任务资料与成果](../index.md)，现行行为仍以[认证底座](../../auth.md)和[认证 HTTP 契约](../../apis/auth.md)为准。§4.5、§5.1 和 §6 是已确认的 R1 实施契约；实际能力由候选验证和接受判断，不改写既有接受事实。

## 1. 摘要

拟为 Mio 建立最小 Redis 运行能力，包括配置、连接生命周期和明确的消费边界；现有 Better Auth 认证限流是首个实际消费者，其计数存储拟从 PostgreSQL 切换为 Redis。项目公共接入通过这个完整业务切片验收，账号、凭据、会话和撤销继续以 PostgreSQL 为准。

首期沿用单实例服务范围。交付目标是项目 Redis 运行契约及首个限流切片的完整行为和兼容证据；性能提升、多实例容量和生产可用性需另有实际证据。优先保留现有限流语义，任何差异先明确接受范围，再实施。

## 2. 使用者与决策责任

- 开发与维护人员：需要明确的计数存储职责、真实调用入口和可复现的验证方式。
- 部署维护人员：需要明确启用条件、故障表现、切换步骤和回退边界。
- 已有账号使用者：注册、登录、续期、退出及撤销等行为应遵循已声明契约，服务中断应可识别。
- 项目负责人决定故障时的可用性取舍、允许中断、计数丢失容忍及实际部署范围；Agent 提出方案、实现已授权内容并收集证据。文档存在、检查通过或任务状态不能替代真实接受。

目前没有证明 PostgreSQL 限流存在性能瓶颈的负载证据；计数已经存入共享数据库，也不能把“从进程内计数变为共享计数”写成本次收益。当前可讨论的价值是验证一个有真实消费者的 Redis 接入切片，以及明确将计数访问从认证数据库移出的成本和效果。

## 4. 目标、范围与成功标准

### 4.1 本期候选范围

- 提供项目级最小 Redis 配置与连接能力，由服务装配管理；认证限流作为首个消费者，覆盖当前库 handler 实际启用的全局、自定义及敏感操作规则。
- 提供最小服务端配置、连接建立与释放、原子计数、过期回收、明确的基础设施错误处理。
- 验证存储选择、已有账号及会话兼容、受控切换与回退，以及必要的源码边界和资料更新。
- 保留 PostgreSQL 限流路径用于既有部署兼容和受控回退；后端在启动时确定，不提供请求级混用或动态切换接口。

项目查询缓存、会话迁移、生成队列、分布式锁、通用缓存框架、多租户、多实例生产部署和模型工具授权均不在本期范围。首期不删除现有认证表，不升级认证库，不同时重写限流算法或代理信任策略。

### 4.2 可观察成功标准

1. 项目有明确的 Redis 运行入口与职责边界；在 Redis 模式下，真实认证请求的限流计数使用该能力，正常计数不再读写 PostgreSQL 限流计数；账号和会话所需数据库访问仍存在。
2. 同一请求序列在数据库基线与 Redis 候选中保持约定的放行、拒绝、窗口及响应语义，并发不会多放行。
3. 原账号、原 cookie、会话续期及撤销行为通过回归；计数故障不会被解释成身份有效或绕过认证。
4. 正常启动、失败启动、运行中断连、关闭、重新装载与受控回退均有匹配候选的证据。
5. 交付前现行规范与实现一致，适用检查及审查齐全；受控本地验证、真实部署观察和远端门禁分别报告。

性能仅记录同负载的数据库计数访问、请求延迟及资源使用。若后续把性能收益列为必需目标，先确认基线、负载及阈值；本草案不虚构提升比例或容量承诺。

### 4.3 复杂度与最小替代

依[底座规则](../../foundation.md#已采用规则与验证)的 DESIGN-OVER-001，保留以下取舍作为评审依据：

| 机制候选           | 具体问题、影响与证据边界                                                           | 最小替代、成本与本期收益                                                                               |
| ------------------ | ---------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------ |
| 引入 Redis         | 目标是验证计数存储改造；现有 DB 瓶颈及发生频率尚无证据                             | 最小替代是继续使用 PostgreSQL；新增服务、凭据、容量和故障维护成本，换取一个真实集成切片的证据          |
| 原子消费与过期回收 | 同一来源可并发请求，分离读写可能超额放行；计数键持续增长需要回收                   | 复用固定库公开的限流存储接口，以一次原子决策实现既有规则；不新增通用锁服务或另一套限流规则引擎         |
| 启动时选择后端     | 既有部署尚无 Redis，且切换失败需要回退；若只能强制启用会扩大升级影响               | 只保留数据库与 Redis 两条有实际用途的路径；不扩展为任意存储插件框架，后续移除兼容路径需独立依据        |
| 故障拒绝及受控恢复 | 新增依赖可能断连、超时或丢失计数；自动转用另一套计数可能放宽限制，发生率待环境验证 | 建议失败时拒绝受影响请求，人工按同一切换步骤恢复；承担可用性成本，避免无依据的双写、自动降级和自动重放 |

### 4.4 公共运行能力与消费者职责

同一个 Redis 技术不意味着所有业务使用同一套策略。首个消费者已经需要配置、连接和生命周期，因此现在划清其归属有实际依据；只实现该切片需要的能力，不预建未来缓存、队列或任意存储框架。

| 职责       | 项目 Redis 运行能力                                                  | 认证限流消费者                                                                    |
| ---------- | -------------------------------------------------------------------- | --------------------------------------------------------------------------------- |
| 配置与连接 | 客户端/服务版本、服务端秘密、连接建立/关闭、运行入口及隔离资源的事实 | 声明自己需要哪个资源及哪些操作，不持有另一套项目公共配置                          |
| 错误与重试 | 暴露可判定的连接失败、超时与结果未知；明确客户端命令重放行为         | 决定计数失败对应的 HTTP 行为、是否可恢复及限流窗口；不把 503 强加给所有未来消费者 |
| 数据与隔离 | 说明资源、命名空间和实例级策略的适用边界                             | 负责计数主体、键结构、原子消费、窗口和恢复；后续缓存的失效/回源由相应业务负责     |
| 模块与装配 | 服务装配管理生命周期；公共运行模块不反向依赖认证或其他业务           | 通过明确依赖消费公共能力，保留库的规则匹配与业务保护                              |
| 规范       | R1 在集成契约目录交付独立的 Redis 现行规范正文与导航                 | 认证规范维护自己的用法、限流语义和接口影响，并直接引用公共契约                    |

具体模块及配置见 §4.5。R1 须交付 [Redis 公共规范](../../integrations/redis.md)、[集成契约导航](../../integrations/index.md)及认证规范的直接引用，在 verify 前纳入同一候选并按 AC-12 核对；正文存在不等于已验证或接受。本 PRD 维护需求与采用决定，不替代未来业务使用 Redis 的现行契约。

### 4.5 R0 公共接入契约候选

本节工程方案已随 §8.2 的 A/B/C 获用户确认，作为 R1 的实施契约。服务端采用 **Redis Open Source 8.2.11**，客户端为官方 **`@redis/client 6.2.1`**，沿用项目 Node 24 与 Better Auth 1.7.18。已复核固定制品并在本机任务可控目录完成安装/编译，未启动全局服务；行为与兼容性仍需在实际候选验证。选择 8.2 系列是因为其属于延长支持系列；精确补丁已在官方发布目录核实。只引入本切片需要的标准命令客户端，不引入搜索、向量、缓存框架或另一套认证库；版本改变须更新契约，不能静默使用 `latest`。[服务版本策略](https://redis.io/docs/latest/operate/oss_and_stack/install/version-mgmt/)、[服务发布目录](https://download.redis.io/releases/)、[客户端固定版本](https://github.com/redis/node-redis/blob/redis%406.2.1/packages/client/package.json)

| 项目         | 候选约定与适用边界                                                                                                                                                                                                                                                                                                                                                                                   |
| ------------ | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 公共运行入口 | 拟新增 `src/integrations/redis.ts`，负责读取 Redis 资源配置、建立连接、执行有界命令及释放；不含认证路径、限额、HTTP 状态或业务键规则。只提供当前消费者实际使用的能力，不导出全功能客户端供业务任意操作                                                                                                                                                                                               |
| 装配与消费者 | `src/plugin.ts` 创建和释放资源，显式注入认证；拟在 `src/auth/rate-limit.ts` 实现库的 `consume` 适配及认证恢复状态。认证继续持有自己的 PostgreSQL 池，其他业务不经认证取得 Redis                                                                                                                                                                                                                      |
| 配置归属     | 公共资源使用 `MIO_REDIS_URL`、`MIO_REDIS_NAMESPACE`；认证使用 `MIO_AUTH_RATE_LIMIT_BACKEND=database\|redis`，缺省仍是 `database`。命名空间为 1–64 位小写字母、数字、下划线或连字符（如 dev-mio），标识环境/服务并保持稳定；测试另用每轮独占值                                                                                                                                                        |
| 启用组合     | 仅提供 Redis URL 不启用限流。数据库模式不连接或校验未消费的 Redis 资源；显式 `redis` 时须有完整认证配置和 Redis URL/命名空间，非法后端或缺项拒绝装载。认证适配以独占探测键执行实际消费脚本，核对 TTL 并删除自己的探测键后才完成初始化（不等待整个窗口）；资源版本/淘汰/持久化策略由操作者预检，不授予应用配置修改权限。未配置认证且未选 Redis 时保持原 Foundation 行为；不暗示 Redis-only 业务已支持 |
| 连接与秘密   | 首期一个独立单节点资源、一个服务实例内复用的客户端；不用每请求连接、连接池、Cluster、Sentinel 或读副本。URL 仅服务端注入，不回显；远程连接使用校验证书的 TLS，本地隔离测试可用回环明文。运行身份仅获自身前缀及必要命令权限，不授予清库或配置修改能力                                                                                                                                                 |
| 时限与有界性 | 首轮候选：连接及启动探测总预算 5 秒、一次消费从入队到结果总预算 1 秒、关闭预算 1 秒、待答命令队列上限 128。它们是首期保护预算，不是延迟/容量实测结论，也不提升为其他中间件默认值；R1 必须验证已发送但不回包的情况                                                                                                                                                                                    |
| 错误与重放   | 公共层提供连接不可用、已知拒绝、超时/结果未知的可区分失败，不返回业务 HTTP 响应。当前限流资源禁用离线队列与自动重连；不得自动重发消费。明确发生在发出前的队列满等拒绝与已发出后结果未知分开处理                                                                                                                                                                                                      |
| 释放         | 创建失败、认证初始化失败、启动中卸载和正常卸载均释放已持有资源。先停止新消费，正常等待关闭；超出关闭预算销毁客户端。销毁或取消不证明服务端已撤销命令，未知结果仍进入 §6 的处理                                                                                                                                                                                                                       |
| 资源策略     | 建议认证计数使用独立 `noeviction` 实例，有限 `maxmemory`；隔离验收先固定 128 MiB，实际部署容量依 R2 环境另定。键前缀/逻辑 DB 不隔离内存与淘汰策略。首期计数采用内存数据、关闭 RDB/AOF，重启视为丢失并执行恢复等待；这不是未来业务持久化的公共默认                                                                                                                                                    |
| 验证资源     | R1 在本机和 CI 使用测试夹具持有的固定版本 Redis 临时进程、回环随机端口和独占目录，支持停止/重启/容量故障；缺二进制或版本不符明确失败，不跳过。PostgreSQL 沿[既有隔离约束](../../integrations/postgres.md#验证入口与变更影响)。不把任意共享 Redis URL 当作故障测试目标                                                                                                                                |

客户端配置依据是固定版本的[连接选项](https://github.com/redis/node-redis/blob/redis%406.2.1/docs/client-configuration.md)、[命令选项](https://github.com/redis/node-redis/blob/redis%406.2.1/docs/command-options.md)和[关闭实现](https://github.com/redis/node-redis/blob/redis%406.2.1/packages/client/lib/client/index.ts)。其中 `commandOptions.timeout`/取消只覆盖尚未写入 socket 的命令，不能单独满足消费总时限；R1 需有总等待期限、迟到结果不得进入认证业务、连接销毁和拒绝重放的组合验证。正常 `close()` 等待待答命令，也不能视为天然有界。

R1 的边界正反例：允许装配入口访问公共 Redis、认证适配消费该能力；拒绝公共 Redis 反向导入认证、DSH、开发脚本/测试，拒绝业务绕过公共入口直接导入 Redis 驱动，拒绝迁移工具借此获得运行时连接。现有 PostgreSQL/Better Auth 导入边界保持原样；R1 已沿现有 AST 检查器和分类范围补入规则与用例，实际执行结论绑定当前候选原件，不从 R0 文档或规则存在推导通过。

未来业务复用时，版本、连接资源、安全边界和结果未知处理进入公共规范；本表的认证资源配置须注明适用消费者。限流窗口、503、故障后停止消费及恢复等待仍由认证规范维护。新缓存需要自动重连、LRU 或持久化时核对资源是否相容，不复制认证策略，也不因新增消费者就重写整个公共契约。

| RL-01 规则等价       | 库继续负责路径匹配、计数主体和规则选择；Redis 仅承担状态消费                                     | 按固定版本建立路径、优先级、窗口、计数更新、重试时间的对照表。错误凭据也计入进入限流器的请求；被 HTTP 适配器提前拒绝的请求不新增计数副作用 |
| RL-02 并发与窗口     | 检查额度、推进计数及设置对应过期时间是一次原子操作；使用有界键和值                               | 不直接把当前行为换成自然分钟桶、令牌桶或简单固定 TTL 计数。窗口边界、连续放行后的时间更新、拒绝是否延长窗口、临界时钟差必须有基线对照      |
| RL-03 响应与身份     | 保留现有路径、方法、Origin、CSRF、正文限制、可信 IP、cookie、安全响应头及超限响应                | 不新增客户端参数、业务身份来源或前端升级要求；已放行请求仍需正常执行凭据校验和资源归属判断                                                 |
| RL-04 会话隔离       | PostgreSQL 保持账号和会话的权威来源，`/me` 继续返回已验证身份且不刷新会话                        | 不把 Redis 当身份缓存或会话来源；原用户、原签名 secret 和原 cookie 不因计数迁移失效；保留密码更新及跨账号撤销保护                          |
| RL-05 配置与生命周期 | 未启用 Redis 时保持数据库限流；显式选 Redis 却配置不完整或启动校验失败时拒绝认证装载，不静默回退 | 配置名、客户端和服务版本、连接/命令/关闭时限在 R0 固定；连接由服务装配统一创建和释放，认证适配通过明确依赖消费，DSH 依赖仍只在插件入口     |
| RL-06 故障语义       | 建议 Redis 消费失败时拒绝受影响请求，映射为基础设施 503，而非额度超限 429                        | 候选错误体沿包装错误 `AUTH_UNAVAILABLE` 和 requestId 约定；需经真实库 handler 证明异常不会被吞掉或变为其他状态。此新增故障策略须先确认     |
| RL-07 数据与资源     | 只存限流计数及窗口所需状态，按服务、环境及模式隔离键；设置容量和回收约束                         | 不存密码、cookie、会话 token；连接秘密仅服务端注入且不入日志。测试只能清理本轮独占资源，禁止对共享实例全库清空；资源隔离方式在 R0 固定     |
| RL-08 计数保留与恢复 | 提前淘汰、重启丢失、写入失败和结果未知都有明确处理；不能把丢失状态直接认作从未请求               | 候选使用避免提前淘汰的部署策略，如 noeviction；容量耗尽拒写仍按 RL-06 处理。持久化不能替代丢失容忍与恢复承诺；见第 6 节                    |

接入点已核对：Better Auth 1.7.18 的公开 `rateLimit.customStorage.consume(key, {window, max})` 返回 `{allowed, retryAfter}`，在请求阶段执行原子消费；指定 customStorage 后优先于 `storage`。候选沿用 `storage: 'database'` 的模型配置，仅由运行时注入 customStorage；迁移工具继续调用原 `authOptions`，不读取 Redis 运行配置或连接 Redis。R1 仍须对账迁移计划。全局 `secondaryStorage` 会影响会话存储，本方案不用它。[固定版本限流接口](https://github.com/better-auth/better-auth/blob/v1.7.18/packages/core/src/types/init-options.ts)、[限流实现](https://github.com/better-auth/better-auth/blob/v1.7.18/packages/better-auth/src/api/rate-limiter/index.ts)、[会话说明](https://github.com/better-auth/better-auth/blob/v1.7.18/docs/content/docs/concepts/session-management.mdx)

`RL-06` 的影响不仅是不能登录：`/api/auth/get-session`、退出、密码更新和撤销等经过库限流的入口也可能因 Redis 故障返回 503，已建立会话仍保存在 PostgreSQL。`/me` 不新增 Redis 调用；服务本身已经装载且数据库可用时应继续按现行契约工作。插件整体重启期间的入口中断另按切换窗口处理，不能承诺零停机。

客户端超时可能发生在 Redis 已消费计数之后。建议保留“可能已计数”的结果，当前请求按基础设施失败处理；不自动重放 consume，不将失败业务请求或认证写入自动重试。客户端离线队列、重连后的命令重放及关闭行为须核对实际库配置，不能让命令在切换结束后再次落入旧后端。

### 5.1 已核对的认证规则与适配候选

依据项目白名单、配置和已安装 Better Auth 1.7.18 的规则解析：先全局，再库敏感规则，再插件规则，最后匹配自定义规则；当前未配置认证插件。下表路径均在 `/api/auth` 下，方法不变。

| 路径                     | 方法 | 实际窗口/额度  | 规则来源           |
| ------------------------ | ---- | -------------- | ------------------ |
| `/sign-in/email`         | POST | 60 秒 / 10 次  | 自定义覆盖敏感规则 |
| `/sign-up/email`         | POST | 60 秒 / 5 次   | 自定义覆盖敏感规则 |
| `/change-password`       | POST | 10 秒 / 3 次   | 库敏感规则         |
| `/sign-out`              | POST | 60 秒 / 100 次 | 全局               |
| `/get-session`           | GET  | 60 秒 / 100 次 | 全局               |
| `/list-sessions`         | GET  | 60 秒 / 100 次 | 全局               |
| `/revoke-session`        | POST | 60 秒 / 100 次 | 全局               |
| `/revoke-sessions`       | POST | 60 秒 / 100 次 | 全局               |
| `/revoke-other-sessions` | POST | 60 秒 / 100 次 | 全局               |

计数原键由库按规范化 IP 与路径生成，查询参数不另开额度；HTTP 适配器仍只传直接连接地址。适配器提前拒绝的 Origin、路径、方法、正文错误及 OPTIONS 不进入消费；库内部的凭据/会话等校验在消费后，失败也占额度。`/api/v1/me`、Foundation 路由及未开放的找回/邮箱修改入口不加入本次限流。由完整表得 **W = 60 秒**，后续增加路径/插件或改规则必须重算。

当前算法按“距最近一次放行是否超过窗口”判断，不是自然分钟桶：无记录或 `now - lastRequest >= window` 时置计数为 1；窗口内未满时加 1，并把 `lastRequest` 更新为本次时间；额度已满则拒绝，计数和时间均不变，等待秒数为剩余时间向上取整。错误密码占用的也是一次放行到业务校验的额度。

Redis 适配候选为单键有界 Lua 消费，复用库传入的 key/window/max，不自行解析路由。键拟为 `mio:<namespace>:auth:rate-limit:v1:<SHA-256(库原键)>`，值只含计数和最后放行时间；摘要用于固定键长度，不当作 IP 匿名化或授权。用 Redis `TIME` 作为该后端的统一时钟，放行时以一次带毫秒过期的写入同时保存状态和窗口，拒绝不续 TTL；写前完成校验，坏值/错误类型报基础设施错误，不能清零放行。脚本只访问一个显式传入键，无扫描、循环增长或阻塞等待；首期直接 `EVAL`，不增加脚本缓存恢复/重试分支。[Lua 原子执行与传参规则](https://redis.io/docs/latest/develop/programmability/eval-intro/)

Redis 时钟与旧后端的应用时钟不同，R1 用相同受控时间序列核对上述转移和边界，再验证真实 HTTP 行为；不承诺两个进程逐毫秒观测完全一致。TTL 与逻辑时间使用同一 Redis 时钟，测试覆盖连续放行推动窗口、拒绝不延长、窗口恰到边界和并发满额。时钟跳变不在正常等价前提内，恢复条件见 §6；如果真实实现改变放行或等待规则，先回到 R0 说明差异，不能以“都叫限流”通过。

2026-11-08 的本轮隔离探针已用真实库 handler 和现有 HTTP 适配器验证上述 9 个规则入参、原始 429/重试头/安全头、consume 抛错映射为脱敏 503、预检/无效 Origin 不消费，以及 `/me` 绕过该消费入口。探针的存储恒拒绝或抛错，身份使用桩；它不证明 Redis 原子性、真实 DB 会话、DSH 装载、迁移或容量，后者全部留在 R1。

## 6. 迁移、回退与故障恢复

### 6.1 数据分类与切换约束

| 对象                | 本期处理                                                                    | 禁止推导                                                       |
| ------------------- | --------------------------------------------------------------------------- | -------------------------------------------------------------- |
| 用户、凭据、会话    | 保留原 PostgreSQL 数据、认证 secret、cookie 和原过期时间                    | 不导出到 Redis，不要求所有用户重新登录，不恢复已撤销会话       |
| PostgreSQL 限流计数 | 保留表与已有数据；切换后停止使用旧计数路径，按已确认策略结束有效窗口        | 停止使用不等于可立即删表，也不意味着旧计数可在任意时间安全复用 |
| Redis 计数          | 仅在隔离、已确认的运行命名空间写入；正常服务重载复用同一状态                | 不通过每次启动更换前缀清空限额；命名空间不隔离实例级淘汰策略   |
| 认证迁移工具        | 继续服务 PostgreSQL 模型；运行时启用 Redis 不应使现有迁移命令要求连接 Redis | 不为计数适配隐式删除库管理的表或改变认证迁移含义               |

### 6.2 首期建议：受控暂停后切换

已确认采用单实例下的受控暂停方案，以避免实时双写和跨存储事务；负责人已接受整进程中断。仓库目前没有统一维护门控，首期由操作者停止整个 Mio Profile 进程，再启动选定后端；因此维护期间认证、`/me`、Foundation 与健康入口均可能不可达，不保证返回维护 503。若目标环境已有可核对的可信边缘门控，R2 可明确其维护响应及覆盖范围；本期不新增管理 API 或运行时切换开关。若要求无中断或其他路由持续可用，先重开方案范围，不能在实现时临时补双写。

按 §5.1 完整规则，当前 **W = 60 秒**。已接受的安排为从最后可能消费时刻起按单调计时等待 **65 秒（W + 5 秒余量）**，在途排清预算 **30 秒**，计划维护预算 **5 分钟**；后者是已接受的计划操作预算，包含停止、等待、启动和核对，不是已测恢复 SLA。时钟前提为应用/Redis 时钟无跳变、核对偏差不超过 2 秒；前提不成立或 30 秒内不能确认旧命令已结束时维持暂停，不能仅靠计时届满放行。超出维护预算需报告并决定继续暂停或完成安全回退，不为守时限绕过窗口。

1. **准备。** R1 先在隔离环境完成本 PRD 的切换/回退及兼容验收。实际切换前固定该候选、旧版本与配置，核对 Redis 版本、凭据、容量、淘汰/持久化策略及隔离资源，备份需要的 PostgreSQL 数据。确认相同数据库和 secret 下的已有账号与会话可用，明确受影响入口、中断预算及操作者；前置证据不齐不开始切换。
2. **阻止新计数请求。** 停止入口及旧进程，排清在途请求；核对旧客户端与服务端待处理命令。不能把客户端连接已关当作数据库/Redis 命令已取消。数据库侧核对本实例会话/语句；Redis 侧核对独占实例无旧消费，无法排清时可在独占资源范围内停止旧 Redis 进程，再按状态丢失恢复。不得以清库替代排清，不重试结果未知的认证写入。
3. **等待旧窗口结束。** 从确认旧后端不再可能消费计数的时刻起等待至少 `W` 加误差余量，确保不存在离线重放、后台写入或仍在服务的旧进程。无法确定该时刻则保持暂停，不能声称计数已安全失效。
4. **启动并恢复入口。** 排清与等待均满足后启动选定 Redis 后端。按现有装配方式，依赖初始化成功即注册路由，进程开始接收流量；没有独立边缘门控就不存在“先现场 HTTP 验证，再开放”的额外阶段。不让新旧后端同时接收同一流量，启动失败保持停止。
5. **恢复后观察。** 核对实际账号/会话、额度及响应，观察 429/503、Redis 错误、键数量和资源使用，以及 PostgreSQL 限流访问是否停止。额度探测使用受控隔离来源，不能清除真实计数或为探测重置生产前缀。保留切换时间、实际中断及异常事实；核对失败立即再次暂停，再按安全回退步骤处理。这一阶段可能已有业务请求，不能声称所有现场验证都发生在放流前。

没有存量计数的全新隔离环境可直接验证 Redis，但不能用该结果证明已有部署的切换。启动前出现超预算、未知写入或前置证据缺失时保持停止；启动后的核对失败则再次暂停。隔离演练中测试客户端暂不发请求，不等于实际部署存在入口门控；必须现场验证后才开放时，先为目标环境明确独立门控并调整取舍 B。

### 6.3 回退及状态丢失

- **计划回退：** 再次停止 Profile，排清 Redis 消费及潜在重放，从最后可能消费时刻等待同样的 `W` 与余量。启动前核对原表与规则；原数据库后端启动成功即恢复入口，随后观察原会话和业务响应，异常再暂停。旧 PostgreSQL 计数应已超过窗口，不能未经核对直接带回有效额度。
- **Redis 运行中故障：** 先按 RL-06 拒绝受影响请求，不自动切回数据库。连接丢失、消费总时限到期、协议/数据异常导致结果或状态未知时，认证消费者停止后续消费，销毁该连接并保持 503，不能因迟到成功或下次 PING 成功自行恢复。仅明确未发出的队列满、或服务端确认未改变状态的拒写，可只拒绝当前请求；不得把未知错误归为此类。故障发生前已取得允许结果并进入业务的请求仍按原认证语义结束，不作补偿或重放。
- **解除停止条件：** 操作者负责暂停/停进程、确认旧写入已终止、等待 65 秒、核对资源并重新启动；不依赖难以证明的“重连后计数完整”。故障后禁止外部进程管理器绕过此过程立即自动重启。正常计划重载仅在 Redis 未重启/清空且旧客户端已经排清时复用原计数；原因不明的重启按故障恢复处理。运行故障期间已装载进程的 `/me` 可继续用 DB，人工停进程期间则不可达。
- **Redis 重启或恢复备份：** 首期建议关闭 RDB/AOF，允许短期计数在 Redis 停止后丢失，依靠停止消费及等待原窗口结束恢复，不允许带流量即时归零。开启 AOF everysec 是可选替代，增加磁盘及恢复维护，仍不承诺零丢失或免除恢复等待；旧备份也不自动代表连续计数。[Redis 持久化](https://redis.io/docs/latest/operate/oss_and_stack/management/persistence/)
- **容量与淘汰：** 缓存类淘汰可能重置限额；选择 noeviction 仍可能因内存不足写入失败，须按故障处理并验证恢复。[Redis 淘汰策略](https://redis.io/docs/latest/develop/reference/eviction/)
- **清理：** 本期保留旧限流表及回退所需代码。只有后续明确结束回退期、确认模型与迁移影响并获授权，才讨论清理；不将删除作为本期完成条件。

上述保护有明确边界：应用能拒绝已观察到的故障，不能自动识别管理员在连接不断开的情况下删除有效键、恢复部分数据或改变淘汰策略。独占资源、运行账户不能清库、禁止带流量运维，以及人工恢复责任是本候选的成立条件；未实现持久恢复控制面或后台状态完整性检测。若目标环境不能保证这些条件，需要另行选择恢复机制，不能据当前探针或 `pnpm check` 宣称已覆盖。

### 8.3 规范、记录与接受

当前独有设计取舍已在本 PRD 表达，不另建空设计文件。必要时增加设计资料并登记到同一 PRD 目录，仍保持需求、现行规范和执行事实各自归属。

R1 实施时将已采用的项目 Redis 配置、生命周期、消费边界和资源约束写入 `docs/integrations/redis.md`，并由[集成契约目录](../../integrations/index.md)导航；[认证底座](../../auth.md)直接引用该规范，维护限流消费者的配置选择与迁移说明，[认证 HTTP 契约](../../apis/auth.md)维护计数来源和故障语义。公共规范、导航及消费者引用是 R1 必交付项，须与实现在 verify 前进入同一候选并由 norms-review 核对，不留到 complete 后补写。模块边界变化同步[源码护栏](../../engineering/source-guardrails.md)，必要启动说明更新 README；按实际实现维护已采用约束，不把未纳入范围的提案写成现行规则。

任务建档、C0/C1、命令型实施、quality-review、norms-review 与真实接受沿[协调协议](../../coordination.md)和[验收入口](../../acceptance.md)执行。仅实际开发能力设置 result；证据齐备后 prepare 私有草稿，真实接受后 complete。旧认证成果只说明原受验范围，不改写成 Redis 已接受；维护与运维记录不为收尾制造公共 complete。

R0 文档和隔离接口探针只说明原受验范围，本机环境准备本身不代表完成。R2 仅在实际选择并授权后成为要求。任何阶段均不据此推导生产容量、邮箱所有权、多实例或后续生成业务已就绪。

### 8.4 后续业务缓存的文档变化判据

假设后续已建立的项目业务需要查询缓存，具体缓存需求仍须单独明确。下面检验资料归属，不把该业务加入本期实施范围。

| 后续变化                                             | 应更新的资料                                                                                                                                            | 保持稳定的资料                                                           |
| ---------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------ |
| 复用现有 Redis 公共契约，新增业务缓存                | 该业务已有 PRD 的目标/验收与执行安排；独立新目标才新建 PRD。采用后在业务现行规范明确权威数据、缓存键/TTL、失效、授权及回源。新 PRD 才新增注册与任务导航 | 公共 Redis 规范、认证规范、本 PRD 及原接受事实无需因“多一个消费者”而重写 |
| 消费者提出新的公共能力，或公共版本/配置/生命周期改变 | 在本次需求解释影响；公共 Redis 规范只更新实际变化，补受影响消费者的回归及必要模块边界检查                                                               | 无关业务 PRD、无关规范和旧接受记录不跟随批量改写                         |
| 业务选择不同缓存/故障策略，公共契约已支持            | 该业务自己的现行契约及验证，引用公共规则                                                                                                                | 不把认证的 503、计数保留、迁移窗口复制为全项目缓存规则                   |
| 实现已接受                                           | 按该 PRD 的稳定成果键登记本次接受，保留旧接受各自的候选边界                                                                                             | 不搬迁 PRD，不将需求正文变成所有消费者的长期公共规范                     |

反例：认证计数使用 noeviction，而新缓存希望采用 LRU 淘汰。两者共享一个实例时，键前缀不能隔离实例级淘汰策略；不能只在业务 PRD 写“使用 Redis 缓存”就认定无公共影响。需要明确资源隔离或相容策略，并验证限流保护和容量影响。相反，公共资源和契约足够承载的新消费者，不应被迫重开认证 PRD。

这里的持续治理判据是：相同公共事实只有一个现行维护位置，变更集中于实际受影响的职责，公共变更能够触发相关消费者验证。资料登记、可达性、候选绑定可由现有工具检查；“复用是否合理、是否重复契约、是否遗漏业务失效语义”仍需实际审阅。场景推演支持该结构设计，但不构成多轮长期运行效果已被证明。
